Ideation: a database for Mo

Focus: database and storage ideas for Mo, either written in Mo or built into the language. Outside the box, novel and ambitious.

Grounding Context

Codebase Context

Seven ideas survived out of 45 raw ones. Five generators produced the 45, they merged into 24, and a verifier with no view of how they were made tried to break each. Nine held. Fifteen were cut. Two of the seven were kept against the verifier's verdict, and each says so.

What the ideas were measured against.

  • The draft. design.md has four layers: Mo, a data store (a tree of nodes written once and named by hash, a log of calls, views kept current), a database (types are the schema, write functions are the only way data changes, promises are checked after each write) and a layer for outside callers (grants, read programs, worlds that land by replay).
  • Robert's decisions. No SQL is presupposed. The ordinary Mo application is the base case and agents are a layer on top. The accountable write is the centre. A read program only reads. Agents propose and a person approves. A world lands whole or not at all.
  • Robert's steer. "Extremely ambitious." The work had become "too focused on what can Mo do today and not what Mo needs to be able to do". Anything Mo gains must be an ability other programs would also use.
  • Already written down. 36 ideas in design-ideas.md. An idea that restated one was cut.

Gaps the draft itself names.

  • No form of a question that the compiler can match to an index. The draft calls this "the largest gap for an ordinary application".
  • Only Mo programs can read the data. Object databases lost to relational ones on this.
  • Erasing a person's data fights history that is named by hash and kept for good.
  • Fairness for an agent that thinks slowly, and which of an agent's reads count as relied on.
  • Sensitivity carried in types has no design.
  • What an agent with no memory is shown first.
  • Whether the store is a library written in Mo or part of the runtime.

Mo as it is today (read from ~/code/mo, branch feat/phase6-review-door).

  • All values are immutable and cannot form cycles. Heap objects are reference counted. A value with one holder is edited in place, and a shared one is copied whole. A Map is one allocation with no sharing between copies.
  • A service is one state type plus pure handlers. A handler holds no capability and gets the arrival time as an argument, so replay is exact.
  • The log stores each call's inputs and a checksum of the state it produced. A whole snapshot is written every 100 messages, and the covered log is deleted. An upgrade also deletes the log's tail.
  • A promise is checked by mo test on generated inputs, not at run time. mo test --strength scores promises against wrong versions of the program.
  • The review door (Phase 6, in progress) checks a pushed candidate's own promises in a child process and holds it for a person unless every approved intent item is unchanged and no migration is named.
  • Mo Core is defined in Lean. The runtime is C. The HTTP layer is written in Mo.

What the research and the web search added.

  • No surveyed database works out what code will read and write before it runs. All learn it by watching the code run.
  • Every store that kept unbounded history later had to add a way to forget.
  • Guards on read freshness needlessly block 92 to 95% of harmless races.
  • Models write SQL correctly from a schema 47% of the time and SPARQL 3.3% of the time. Worked examples lifted SPARQL to 76%.
  • Documented agent incidents came from broad credentials and no approval step, not from missing concurrency features.
  • Earlier work that came closest: Napier88 and Motoko (persistence in the language), Unison (code by hash), Cozy and Chestnut (layouts made from the program's own code), Salsa and Skip (recompute only what changed), Froid and QBS (ordinary code lifted into query form).

Topic Axes

  1. The store underneath. Bytes, layout, versions, memory and disk, forgetting.
  2. Asking. How a question gets answered with no query language: indexes, views, saved answers, readers that are not Mo.
  3. Changing and keeping true. Writes, promises, history, changing the shape of data.
  4. Sharing among many callers. Worlds, landing, grants, sensitivity, agents and people together.
  5. The language boundary. What the compiler, the type system and the runtime can do for data that no library could.

Ranked Ideas

  1. Plain Mo is the query language Asking
  2. One history across upgrades, and a door that replays it Changing and keeping true

How the seven fit together. Idea 2 keeps the log whole. Idea 4 records what each read depended on. Idea 5 needs both. Ideas 1 and 4 share one compiler pass over Mo Core. Idea 6 is the floor the others would stand on if the store became part of the runtime. Ideas 3 and 7 stand alone.

1. Plain Mo is the query language

  • Axis: Asking
  • Confidence: 70%
  • Complexity: High
Description

Add no query language. In time, drop the index lines too. The compiler lowers every read function, and every read program an agent sends, to Mo Core and rewrites it to one normal form. Filters are fused. A filter of the shape "key of the row equals a value" becomes "group by that key, then get the value".

Each piece of the normal form that reads a stored table is named by its hash. The same piece then has the same name wherever it appears: in a page handler, in an agent's program, or in an index line. The store keeps a named piece current as a view, and every read that contains the piece uses the view. A declared index is a piece the programmer pinned. A piece that keeps coming back is kept without anyone asking.

The plain walk stays the specification. mo test runs each rewritten query and its plain form on generated data and requires the same answer, the way it already runs the recovery check with nothing written by the author.

Promises go through the same pass. The compiler works out how each write function can change each promise and builds what makes the check cheap. A per-row promise is checked on changed rows only. "Email is unique" creates the index by email. "The sum of balances equals what was issued" becomes a sum kept current. The compiler says which promises it could make cheap and which still walk.

fn orders_of(shop: Shop, b: Int) : List(Order)
  shop.orders.filter(fn(o) o.buyer == b end)    # normal form: G#a91c.get(b)
end

index orders_by_buyer: orders by buyer           # the same G#a91c, pinned
Basis

direct: "A question nobody declared an index for walks everything. Nothing chooses a fast route, as a query planner does." (design.md:107). "Only some views can be kept current." (design.md:152). "A promise is checked by mo test only, so a rule is written twice" (design.md:279). The research found that agents' queries repeat heavily: distinct sub-plans are often under 10 to 20% of queries.

external: Value numbering in compilers (Alpern, Wegman and Zadeck, 1988). View matching in SQL Server (Goldstein and Larson, 2001). Froid and QBS, which lift ordinary code into query form. Cozy and Chestnut, which make layouts from a program's own collection code. Models write SQL correctly 47% of the time from a schema and a new language far less.

Rationale
Robert asked how an ordinary web application's data "get[s] queried", and the draft calls this its largest gap. Agents already write Mo, and a new language would cost them accuracy. A declared index and a question nobody planned meet at one name, so there is no planner to build and no second language to teach. The verifier found this the hardest idea to break. The conserved-sum half of a cut idea (a sum that must not change, checked on the changed rows) lives on here.
Downsides
  • Splitting a closure into "the key" and "the value it is compared with" will not always work. Code outside the shapes the rewriter knows still walks. The compiler must say which shape it missed, or the walk is silent.
  • Knowing which pieces come back needs reads in the log. Today a read is not logged, and the log holds no instruction counts. The verifier caught a claim that it did.
  • View matching is old in SQL engines. What is new is doing it over a general language's core, with the plain walk as a tested oracle.
  • Joins, minimum and maximum are costly to keep current. A promise with no cheap form still walks.
  • Mo must gain a normaliser over Mo Core, an ordered index and names by hash. Every Mo program would get shared sub-expressions and fused loops from the same pass.

2. One history across upgrades, and a door that replays it

  • Axis: Changing and keeping true
  • Confidence: 75%
  • Complexity: High
Description

Two statements in the draft contradict each other today. "The log is the truth." And "a change of shape is an upgrade of the program". In Mo an upgrade writes a snapshot and deletes the log's tail, so every deploy cuts the truth short. No replay can cross one.

Make an upgrade one more entry in the log of calls. It runs like a write: whole or not at all, promises checked after, who and why recorded. With it comes a call migration: a pure function, checked by the compiler, that turns a call to an old write function into calls to the new ones, or refuses it. A world opened before an upgrade then lands by replaying its calls through that migration. Audit, undo and taking one agent's work out all work across deploys.

Once the log is whole, the review door can use it. Its check child replays the last N real calls through the candidate, on a fork of the current root, and compares each reply and each resulting root with what the old code produced. The person reads what would now behave differently, not a text diff.

9041 place_order@a1f3(buyer: 7, item: 3, count: 2)     by web:ana
9042 upgrade a1f3 -> c77e                                by robert "split stock by warehouse"

fn migrate_call(old: UpgradeOld.PlaceOrder) : PlaceOrder
  PlaceOrder(buyer: old.buyer, item: old.item, count: old.count, warehouse: 1)
end

door: replayed 18,204 real calls. 18,161 identical.
      43 differ: place_order now refuses count = 0 (was: stored an empty order)
Basis

direct: "The new typed host operation performs, in one SQLite transaction: new snapshot at the current head, tail deletion, program replacement" (~/code/mo/docs/design/upgrades.md:118-119). "The log is the truth." (design.md:189). Mo's Phase 6 plan lists "Checking promises against a live service's recorded messages." as left out (~/code/mo/docs/plans/2026-11-12-1604-feat-phase6-intent-autonomy-plan.md:173). The research records that mo test passed a duplicate-key bug because its generator never made a duplicate key.

external: Napier88's own papers name the evolution of data and programs as the unsolved part of persistence in a language. Golem replays a log of effects against new code. Shadow-traffic comparison (Diffy, Scientist) is the close earlier work for the diff.

Rationale
It removes a contradiction at the centre of the draft. It also gets stronger every day the service runs, because the test inputs are the real calls. It is the clearest case of the database giving something back to the language: Mo's door, which is being built now, would gain a check no generated input can match. Ideas 4 and 5 need the unbroken log this provides.
Downsides
  • Old code must stay runnable, by hash, for as long as the history is kept.
  • Replaying a long history through many migrations is slow.
  • The same answers on recorded calls is evidence, not proof. The diff informs a person and never replaces the approval. A variant that let a refactor pass the door unattended on this evidence was refuted for that reason.
  • One old call may need to become several new ones, or be refused. The first sketch typed it as one to one.
  • Replies are not in the log today, and a snapshot deletes the log it covers.

3. Held(T): absence as a type

  • Axis: The language boundary
  • Confidence: 70%
  • Complexity: Medium
Description

A field typed Held(T) is stored in history as a reference. The bytes live in a small vault outside the hash-named tree, keyed by the person they belong to. Reading the field gives Present(v) or Erased, and the compiler requires both arms.

Erasing a person deletes their vault entries. Every hash, every root and every log entry stays valid, because history only ever held the reference. mo test generates Erased among a type's extreme values, so every promise is also checked on erased data.

The same type can carry how long a value is kept (For(90.days), Until(erased), Kept), and only a release function a person approved may open many Held values at once. That gives sensitivity a first design that needs no tracking of how data flows through a computation.

struct Student
  id: Int
  email: Held(Text)
end

fn greeting(s: Student) : Text
  case s.email.open()
    Present(e): "Hi " + e
    Erased: "Hi, former student"
  end
end
Basis

direct: "Names by hash fight erasing. Erasing a row from an old version changes the hashes above it. The store can leave a marked hole where a node was. This is not designed yet." (design.md:151). "Need 5. Sensitivity that travels in the types is an idea with no design, and Mo has nothing for it." (design.md:248).

external: The research found that every system with unbounded history later added a way to forget, and that guidance points to personal data held outside the history, by reference. Destroying a key to erase data ("crypto-shredding") is the known answer in event-sourced systems (research/05-databases-that-keep-history.md).

Rationale
The usual fix is a hole that every reader must remember to handle, and readers forget. Mo has no null and no exceptions, so a forced Erased arm fits the language as it is. Two gaps the draft lists apart, erasure and sensitivity, share one cause: the data sits inside the history. Four of the five generators arrived at this idea separately.
Downsides
  • Replay. A write function that opened a held value and branched on it gives a different state after the value is erased, so the logged checksum no longer matches. The verifier noted that "every checksum stays valid" holds only if no write depends on an opened value. One rule that would make it hold: a write function may move a held value but not open it. Uniqueness checks would then need a stable token in the reference. This is the main open design question.
  • Derived data still holds what was erased: indexes, saved answers, and anything that already left.
  • Retention on every field is friction, and flows through control (not only through values) are hard to check.
  • Mo must gain a wrapper type that user code cannot forge or unwrap except through open, and a place outside the tree. Any program that holds tokens, keys or credentials that can be revoked would use it.

4. Footprints: every run yields what it read

  • Axis: The language boundary
  • Confidence: 60%
  • Complexity: High
Description

A run of a pure function over stored data gives two things: its result and its footprint, the set of rows and key ranges it read. There are two ways to get one. The compiler works out a cautious footprint from the code before it runs. The runtime records the exact one while it runs.

The store can keep a footprint, compare it with the rows a write changed, and intersect it with another. A program cannot look inside one, so no program can branch on how the data is laid out.

$ mo footprint place_order
reads   stock[item]
writes  stock[item], orders.add

world 7 (agent b): a premise moved   stock[17]: 4 -> 2   (asked at root 41, now root 58)

What follows from the one mechanism:

  • A saved answer or a view is reused when no changed row falls in its footprint.
  • A promise is rechecked only where its footprint was hit.
  • At landing, a question whose footprint no landed write touched keeps its answer without being asked again.
  • An open world is told while it thinks that something it relied on has moved, not forty minutes later at landing.
  • Two write functions whose footprints never meet can be applied in either order. Later, Mo could run such messages on separate cores.
Basis

direct: "A question whose answer those rows cannot have changed needs no second reading." (design.md:240). "Which reads count. An agent reads much that it does not rely on." (design.md:251). The research: "a whole-program compiler deriving conservative read/write sets and checking effects BEFORE execution is done by no production DB found."

external: Salsa, Skip and Adapton track what a computation depended on and recompute only when that changed. Calvin and Aria order work by read and write sets.

Rationale
Four items the draft leaves open share one cause: nothing records what a read depended on. They are asking again at landing, which reads count, views kept current, and the cost of checking a promise after each write. One primitive turns all four into consequences. Mo has an advantage here that Convex and Calvin lack: the code is known before it runs.
Downsides
Kept against the verifier. It ruled this weak. Its points: the run-time half restates "ask again only about what changed"; a footprint made of node hashes would let a program branch on layout and break replay; and the 92 to 95% over-blocking would apply to a cautious footprint too. The second is met by making a footprint opaque. The third does not apply, because a footprint is used only to skip asking again. When it is hit, the question is asked again and judged by its answer, as Robert decided. The verifier itself called the compile-time half "the genuinely open one".
  • A key computed from data, or a walk over a table, widens the footprint to the whole table, and the gain is gone. Agents' read programs often walk.
  • Sums, minimum, maximum and joins need coarse footprints that are right without being hit by every write.
  • Mo's heap has no names for nodes today. A footprint is cheap only once it has.
  • A footprint stored for every read makes the log grow faster than the data.

5. Recall notices: trace a bad write forward

  • Axis: Sharing among many callers
  • Confidence: 55%
  • Complexity: High
Description

A factory cannot un-sell a bad lot. It can name every buyer, because each shipment recorded its lot, and send a notice. Treat every answer that left the store the same way: the result of a read program, a release, a reply to a page.

The store keeps each answered question with its caller, its version and its footprint. When a write function is found faulty, or one agent's work is taken out, the store builds the corrected history. It then asks again each shipped answer the correction could have touched, on the corrected version. Every answer that comes out different becomes a typed recall record: who received it, what they were told, what is now true, and which of their later calls relied on it.

The same records answer two other questions by lookup. "Who has ever read this student's record?" is the disclosure record that school and health privacy law asks for. "This row was written by an agent that had been tricked. Which later answers and writes read it?" is the spread of the damage.

r = shop.recall(code: hash#4f2e)            # or shop.recall(caller: agent_17)
for n in r.notices
  notify(n.receiver, n.was, n.now, n.later_calls)
end
Basis

direct: "It cannot recall anything that already left through a release function." (design-ideas.md:316). "The program, its caller, the version and the answer are recorded." (design.md:229). "Taking one caller's work out is replaying the log without its calls" (design.md:189).

external: Warp (SOSP 2011) re-runs new code on old inputs but repairs only stored state. Retro and Warp paid 24 to 127% overhead to track dependencies. EU food law (Regulation 178/2002) requires tracing "one step back, one step forward".

Rationale
The project wrote this down as something that cannot be done and stopped. A recall turns "cannot unsend" into a list of everyone who was told something false and what to tell them now. It completes the accountable write: who, under which grant, why, and what they saw. That is what a person needs before trusting what agents did.
Downsides
  • It needs reads in the log with their footprints, and a log that is never cut. So it needs ideas 2 and 4 first.
  • Asking every shipped answer again costs as much as all of them together, unless footprints skip most.
  • A footprint per read makes the log grow faster than the data.
  • A notice says what was wrong. It cannot undo what the receiver did with the answer outside the store.

6. The store is the heap

  • Axis: The store underneath
  • Confidence: 40%
  • Complexity: High
Description

Do not build a store beside Mo's heap. Let Mo's own collections live on disk. A large Map, Set or List gets a tree form whose nodes are written once and carry a hash of their contents. The runtime reads a node in when a program touches it.

A service's saved state is then already a tree with versions. The checksum of the whole state that every log record carries today becomes the hash of the root. A write costs one path, not the whole state. Every existing Mo service gains this with no database library, and the database becomes a thin layer of types on top.

Two things follow from what Mo already guarantees.

  • Garbage is exact. A Mo value cannot reach itself, so a count of holders frees everything. Kept on disk, the count frees a dropped world or an old version at once, with no collector that traces the whole store.
  • A read from disk stays pure. Reading a node named by its hash always gives the same value. It needs no capability and cannot disturb replay. The runtime sees the program's loops, which no database server can, so it may fetch the next nodes before the loop asks.
Basis

direct: "So no value can reach itself, reference counting reclaims everything, and no cycle collector is needed." (~/code/mo/docs/design/architecture.md:1392-1393). A log record holds "the FNV-1a checksum of the saved state the message produced" (~/code/mo/src/base/log-record.h:6-10). "Reads hop from node to node" (design.md:109). The draft leaves "library or runtime" open and leans to the library (design.md, section 9).

external: Btrfs keeps a count per block (Rodeh). A Datomic user held over 900 GB of garbage for about 40 GB of live data. Napier88 made data persist by being reachable. Motoko keeps main memory across upgrades and checks its shape at each one.

Rationale
This is the plainest answer to "built into the language". It turns four lines of the draft's list of what Mo must gain (a hash, data outside the one saved state, collections that share what did not change, reads during a write) into one change to what a Mo collection is. Every store that keeps versions was hurt by garbage, and Mo's values make garbage a local, exact step. It takes the opposite side from the draft's lean to a library, which is why it is worth a meeting.
Downsides
Kept against the verifier, and narrowed. It ruled the first version weak, and three of its points stand. The heap's cached hash is keyed with a secret for each process, and FNV is not a hash that can name content, so Mo needs a real one. Rewriting an unshared node in place across commits would break the order that makes a crash safe, so that part is dropped. A read from disk can fail and Mo has no exceptions, so a failed read must fail the whole message, as a handler failure does now. The thesis passed the verifier's meeting test and the bundle did not.
  • Counts on disk that survive a crash took Btrfs years.
  • A tree form may lose the speed Mo gets from a small Map being one allocation edited in place.
  • The steps that touch the disk move out of Mo code, where they can be simulated, into the C runtime.
  • It extends "library versus runtime" in design-ideas.md. It does not replace it.

7. The data teaches by example

  • Axis: Asking
  • Confidence: 60%
  • Complexity: Medium
Description

The store records every read program with its answer, its cost and its caller. It promotes good ones into example rows on the types. A good one has run several times for at least two callers, is cheap, has a shape unlike the ones already kept, and passes under the grant's view alone.

Mo already compiles example rows, names them by digest and runs them under mo test. So a promoted example is checked again at every upgrade, and one that no longer compiles is withdrawn. An agent with no memory is shown the types in plain words, the promises as sentences, a few rows of each table as its grant sees them, and the top worked questions run again with today's answers.

example "orders for one email"
  orders_of(shop, "ana@example.test") -> [Order(buyer: 4, item: 9, count: 2)]
end

$ modb orient --as agent-b
types, promises in plain words, 3 rows per table, 12 worked questions with answers as of root 58
Basis

direct: "Need 6. What an agent with no memory is shown first." is listed as not designed (design.md:249). "An intent item is one promise, one service promise, or one example row" (~/code/mo/docs/design/intent.md:145).

external: The research found that models write correct queries from a schema alone 47% of the time for SQL and 3.3% for SPARQL, and that worked examples lifted SPARQL to 76%.

Rationale
Every new agent works out the shape of the data again, and a guide written by hand goes stale. Here the guide is made of programs that are compiled and run, so one that has drifted fails loudly. mo guide teaches the language. This teaches the data, which is what an agent with no memory meets. The verifier judged it new for this gap.
Downsides
  • A real row promoted into an example becomes part of a source bundle, which is named by hash and kept. That defeats erasure. Examples must use made-up rows, or held values that stay behind their reference (idea 3).
  • "A good example" is a judgment nobody has measured.
  • Mo must be able to accept a caller's program while running and promote it to an intent item.

Rejection Summary

Two of these are sound and were cut only for being the least new. They are worth doing as a matter of course: rows 1 and 2.

#IdeaReason Rejected
1Published copies for readers that are not Mo: an approved release kept current as a read-only SQLite file, stamped with its rootSound, and it answers what sank object databases. Cut on the stricter pass as the least novel: it is the known "relational copy beside the store" pattern with a stamp.
2A grant says what must stay unchanged: a changes filter checked against the rows a write changedSound, and it answers an open question in design-ideas.md. Cut as close to SQL row security with a check clause. The new part is small.
3Landing slots and leases on answersBrings locks back under another name. A footprint is known only after a world has read, so order by filing does not help the slow thinker it is for.
4Speed is intent: a query's cost class checked at the review doorContradicts itself. An intent digest is equal or not, with no direction, so the door would hold the index that makes a query faster.
5The walk is a capability, and every question gets a quoteBelow the floor. A walk is not an effect on the outside world, and the instruction limit already bounds every walk.
6An engine compiled for each program, checked against a reference storeToo costly for its likely value. Years of research with no decision to make now, and a cited number was wrong.
7Upgrade by node, each distinct node migrated once and rememberedThe claim that a bad upgrade is undone by switching the root back is unsound: it discards every write since. Converting on first read is old.
8Identity that follows behaviour: a refactor passes the door unattended if it matches on all recorded callsBasis refuted. The same answers on history is evidence, not proof, and it would weaken "a person approves".
9Promises mined from historyBelow the floor. It is data profiling, a known tool, and the strength score has nothing to measure for a mined promise.
10Worlds live in a nursery: a world's changes stay in memory until landingAn optimisation of something that already costs one root. No open decision.
11History as checkpoints plus replay, on a stated budgetBasis refuted. The checkpoint schedule it borrows serves one backward pass, not reading any past version, and the stated bound cannot hold for history without end.
12Mo Core as the archive formatThe "few hundred lines" evaluator is not credible, and it would not serve a reporting tool.
13"Since I last looked": a hash-chained log as a unit of reviewDuplicates known practice and "the log is the truth". The proof it offers is the entries themselves.
14What you may write depends on what you have readThe right question, the wrong mechanism. A trust class taken from the last writer is laundered by any trusted function, and Mo cannot yet tell callers apart.
15Approve answers, not diffs: standing questionsWeaker than what it replaces. The research says approval should bind to the changed rows. Anything no standing question watches goes through.
16Conserved quantities and linear rows as typesLinear rows need a large change to a language whose values are freely shared, and the cited basis was about memory, not logic. The conserved-sum half lives on in idea 1.

Every axis has at least one survivor. Not every basis got the same scrutiny: the two generators that held the most ideas spent their reads across more of them.

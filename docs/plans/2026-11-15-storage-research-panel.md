## Prior work on the choice itself

- **"Bulk Types: Built-In or Add-On?" (DBPL, 1991).** "built-in Advanced Bulk, as elaborate as it may be, frequently does not cover the whole range of demands of a fully-fledged application and often does not provide a decent pay-off for its implementation effort." It favours "bulk types as add-ons" over a core with the right primitives. [paper](https://cs.cit.tum.de/fileadmin/w00cfj/sebis/publications/MaSc91b.pdf). Checked.
- **"Lessons of Persistence and Upgrade: In Praise of Manual Persistence" (the E language).** Transparent persistence solves surviving a crash, but not surviving an upgrade: "The upgrade problem occurs when we wish our application data to survive a different kind of trauma -- the upgrade of the code". [page](http://erights.org/data/serial/jhu-paper/upgrade.html). Checked.
- **"Implementing Orthogonally Persistent Java" (ANU-OPJ).** Persistence with no change to the virtual machine, and a store kept apart behind an interface with three implementations. [paper](https://www.steveblackburn.org/pubs/papers/opj-pos9.pdf).
- **"Can Java Persist?" (1996).** Names the low-level facilities that let evolution and other persistence features be written in the language. [paper](https://archive.cs.st-andrews.ac.uk/papers/download/MCK+96.pdf).
- **"Smarter Contract Upgrades with Orthogonal Persistence" (VMIL 2024).** The design of Motoko's persistent heap: a self-describing layout and a compatibility check at every upgrade. [paper](https://concurrency.ch/Content/publications/Blaeser_Russo_Smarter_Contract_Upgrades_Orthogonal_Persistence_VMIL_2024.pdf).
- **"Are You Sure You Want to Use MMAP in Your Database Management System?" (CIDR 2022).** The costs of letting the OS page data transparently: writes reach disk before commit, I/O errors are hard to handle, stalls. [paper](https://www.cidrdb.org/cidr2022/papers/p13-crotty.pdf).
- **"Counting Immutable Beans" (Lean 4).** Exact reference counts on immutable values with no cycles, in a C runtime. [paper](https://arxiv.org/pdf/1908.05647).
- **AutoPersist (2019).** Argues a persistence library such as PMDK puts too much on the programmer, and moves persistence into the Java runtime. [write-up](https://pirl.nvsl.io/2020/02/04/pirl-2019-developing-programmer-friendly-frameworks-for-nvm/).

## What it shows for the three options

- **The runtime option makes the runtime's layout of values a schema that lives for ever.** PJama struggled with class evolution and JVM changes, and was stopped. Motoko made it work, but it took a custom heap layout, a compatibility check at every upgrade, and two years from beta to the only mode. E's paper says transparent persistence solves crashes, not upgrades. Rows 3, 8, 9; prior work.
- **Hiding the disk behind ordinary reads hides failure.** Rows 4 and 7, and the mmap paper. The simulation testers (row 26) run real code against a simulated disk through one point they control. This favours a store whose disk steps pass through one capability, as in L and S.
- **Reference counts kept on disk are fragile; sweeps from the roots are the common alternative.** Btrfs's own developers call that code fragile, though it has run for over a decade. Git sweeps from the refs, and Datomic sweeps on request. Values with no cycles make in-memory counts complete, not crash-safe ones. Rows 12, 18, 19, 24.
- **A sweep nobody runs costs space.** Datomic: about 900 GB on disk for about 40 GB live. Retention and collection must be explicit policy. Rows 20, 21.
- **Mechanism in the runtime and policy in the language has precedent.** "Bulk Types: Built-In or Add-On?", E, ANU-OPJ and Unison's storage abilities all split it this way. The opposite complaint is real too: a pure library put too much on the programmer (PMDK). Row 31; prior work.
- **The stores still in wide use are libraries.** SQLite, LMDB, Mnesia and Irmin. GemStone/S is the long-lived runtime store, with far smaller reach. Rows 5, 11, 13, 17, 27.
- **A format only the language can read limits who can use the data.** It is true of persistent languages, and largely of object databases, though Versant added SQL. Rows 2, 6.
- **Forgetting is not universal and must be designed in.** Datomic Cloud still cannot excise. Crypto-shredding is the usual answer for immutable history; with content-addressed nodes it means encrypted values no longer share a hash across people (inference). Rows 22, 23.

- Whether on-disk counts are unsafe through a crash, as against complex. One recovery firm's page against the Btrfs maintainer's account.

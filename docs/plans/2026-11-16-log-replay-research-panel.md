## Prior work on the question itself

Found by the members and not in the claims. Claude fetched all but the second and the last.

- **Fowler, "Event Sourcing" (2005), section "Code Changes".** <https://martinfowler.com/eaaDev/EventSourcing.html>. "We can think as three broad kinds of code changes here: new features, defect fixes, and temporal logic." For the first two, running old events through new code is the point: "you can just reprocess the events and the new results pop up", and after a fix "Your application state is now fixed to what it should have been." His events are inputs that the code processes again. For the third kind, primary reads him as saying the rules of each date must stay in the code.
- **Fowler, "Memory Image" (2011).** <https://martinfowler.com/bliki/MemoryImage.html>. It names migration as the known problem of rebuilding state from a log, and advises logging plain structures, not serialized classes (primary's reading).
- **DBOS, "Upgrading Workflow Code".** <https://docs.dbos.dev/typescript/tutorials/upgrading-workflows>. "DBOS supports two strategies for safely upgrading workflow code: patching and versioning." The same pair as Temporal, in a system whose log is in PostgreSQL.
- **The full-sync shim in EIP-4444.** <https://eips.ethereum.org/EIPS/eip-4444>. "We suggest that a specialized “full sync” client is built. The client is a shim that pieces together different releases of execution engines and can import historical blocks to validate the entire Ethereum chain from genesis". Each stretch of the log runs on the release of its time.
- **"Replay Is a Family of Assertions: Fork-Safety in Event-Sourced Agent Runtimes" (arXiv 2611.06924, November 2026).** <https://arxiv.org/html/2611.06924v1>. It separates four things that are all called replay: folding events into state ("projection"), running the code again and getting the same steps ("strict execution replay"), carrying on from a point, and matching the outside world. It "separates facts from effect requests". A manuscript with a small corpus; useful for its words, not as proof.

- **Four more named by the recency member, not fetched by Claude.** [Dapr Workflow versioning](https://v1-20.docs.dapr.io/developing-applications/building-blocks/workflow/workflow-versioning/), [Cloudflare Workflows](https://developers.cloudflare.com/workflows/get-started/guide/) and [Inngest](https://www.inngest.com/docs/durable-execution/durable-workflows) are more engines that record each step's result and skip finished steps on replay. [EclipseStore](https://docs.eclipsestore.io/manual/intro/welcome.html) stores the object graph itself and keeps no journal of commands.

## What it shows for the four options

- **Nobody runs a kept log through freely changed code.** Every engine that replays across a code change keeps the old code alive, in one of two ways: both paths in the code behind a marker (Temporal patching, Durable Functions orchestration versioning, DBOS), or each run held on the build that started it (Temporal Pinned, Restate). Rows 1, 2, 3, 7 and 8. Option D is the second way: each call runs under the code of its own version. In the last year Temporal moved to recommend the second way, and Durable Functions the first.
- **Those engines keep old code only until its runs are finished.** Temporal says the old path can be removed once its runs "have left retention" (row 2). D asks for it to be kept for good. The one system here that does that is Ethereum (row 23), and EIP-4444 was written to let clients stop (row 24).
- **A log that is run again for recovery is a tail everywhere.** Temporal caps a history and starts a fresh one from carried state, and in March 2026 previewed doing that at an upgrade ("Upgrade on Continue-as-New"), which is the shape of option C. Golem replays from a snapshot. Raft, VoltDB and Redis discard what a snapshot covers. Rows 4, 9, 19, 20 and 21. This is option A, and it is what Mo does today. It supports the plan's point that the recovery tail and a kept record are two things.
- **An upgrade by a function from old state to new, with no replay, is the common way.** Motoko, Erlang and Golem's manual update. Rows 9, 10 and 11. Mo does this today.
- **A record kept whole to be read is common, and it holds what was decided, not what was asked.** Akka and KurrentDB keep events for good and translate old ones when read. Rows 12, 14 and 16. The systems that log calls keep them only to the next snapshot: VoltDB, Redis, Prevayler, and Mo. Rows 15, 20 and 21. Mo's log holds calls. Inference: a record meant only to be read or rebuilt from could hold what each call changed, and would then need no old code. Taking one caller's work out still needs the calls, because the later calls must be run again without it.
- **Keeping everything makes erasing a separate, heavy step.** KurrentDB needs a scavenge on every node and cannot take one event out of the middle. Akka warns that deleting events loses the history. Rows 13 and 25.
- **Running old calls through new code on purpose is a fourth use, and the plan does not list it.** Fowler's bug fix: correct the code, run the calls again, and the state is what it should have been (row 16 and prior work). It needs a record of calls, not of what they changed. It is the opposite of D, which wants the same result as before. Mo's recovery forbids it today: a row whose checksum differs is an error.
- **A kept history is also a test.** Temporal recommends running recorded histories through new code in CI, and Golem's automatic update fails when the replay diverges. Rows 6 and 9. A record can serve this use without being the way the state is recovered.

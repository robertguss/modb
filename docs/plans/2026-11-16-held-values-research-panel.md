Created: 2026-11-16

Evidence for [the plan for Decision 4](2026-11-16-1142-decision-4-held-values-in-writes-plan.md). ## Prior work on the question itself

Found by the members, outside the claims. Claude fetched each page.

- **ankka, a platform with a `Personal` field type.** A handler reads `Present` or `Erased`. "Write a handler so that an erased field is an ordinary case". Erasing destroys the person's key and nothing is rewritten. For lookups it keeps "an HMAC-SHA-256 of the field and its value under the project's lookup key", and at erasure "the row's lookup tokens of that subject's fields are dropped". After erasure, an entity's "next write of a personal field of the erased subject is refused". [Page](https://docs.ankka.cloud/build/personal-data/), undated. Claude could not judge who uses it.
- **es-entity, a Rust library.** The held field is an opaque type, and the opened reference cannot be written back: "`ForgettableRef` intentionally does not implement `Serialize`, preventing accidental re-serialization of personal data into secondary stores." The same page says of two of its rules: "Compile-time enforcement of these two rules is deferred." [Page](https://galoymoney.github.io/es-entity/forgettable.html), undated.
- **One design splits the answer by who reads.** "Aggregate replay fails loudly (aggregate state is unrecoverable without the missing event)", while projections skip the event. [Synapse ADR 0036](https://github.com/ianunruh/synapse/blob/main/docs/adr/0036-crypto-shredding.md), undated.
- **Keeping the outcome of a decision as its own event.** "Store the outcome of a decision to guard against rule changes." [Decision tracking](https://verraes.net/2019/05/eventsourcing-patterns-decision-tracking/), 2019-05-29. The argument is about changed rules; that it carries to erased inputs is inference.
- **Keeping part of a value in the clear.** Axon's `partialValueForStorage` "may return a piece of clear text data … which will be stored alongside the encrypted data", with the example of keeping the year of a date of birth. [Axon, advanced](https://docs.axoniq.io/axon-framework-reference/5.4/data-protection/advanced), undated.
- **A store that gives back an empty value cannot tell erased from zero.** "Ordinary reads cannot distinguish an erased `0` or `false` from a genuine value." After erasure a new value for that person "fails with `EncryptionKeyErased`". [Cratis Chronicle](https://cratis.io/concepts/event-sourcing-gdpr), undated.
- **A reference made from the value's own bytes can confirm a guess.** "a guessable payload such as an email from a small candidate list can be confirmed against it." [GenesisDB](https://docs.genesisdb.io/technical-insights/gdpr-support), undated.
- **The EU board's newer text follows the court.** "whether information is personal may vary from one entity to another." [Guidelines 02/2026 on anonymisation](https://edpb.europa.eu/system/files/2026-07/edpb_guidelines_202602_anonymisation_v1_en_0.pdf), adopted 2026-07-07 for consultation.

A paper was found and not read: "Cryptographic Enforcement of Language-Based Information Erasure" (https://people.seas.harvard.edu/~chong/pubs/csf15_crypto_erasure.pdf). It is a lead, not evidence.

## What it shows for the five options

- **A held value is not new.** The pattern is from 2019 (row 6), and two libraries put the two cases in a type (row 27). What none of them has is a rule that a write may not open one while a reply may.
- **In use today, code reads the erased case afterwards.** Every library checked gives a stand-in or an "erased" case and carries on (rows 2, 5, 27). That is option D for reading. None of them promises that the record can be run again with the same result, and one blog says that is what is lost (row 7).
- **Engines that do run a record again keep the answer.** They never work a result out twice (row 12), and a payload they cannot read stops the run (row 9). That is the move option C makes. Inference: C is the option that keeps both a kept record and erasing.
- **"Is this email taken" is checked outside the record everywhere** (row 17), in a table that can be changed, and the one platform that keeps tokens drops them at erasure. So the check's answer does not come from the record. A later run gets a different answer unless the first answer was kept. This supports the plan's worry about option A, and experiment 20 still has to show it.
- **A kept token is the person's data for whoever can still link it** (rows 19 and 20). It stops being linkable when the secret is deleted (row 21). A token that says "same email" across people needs a secret they share, which cannot be deleted for one of them. Inference: such a token must go at erasure.
- **The EU board advises against keeping even encrypted personal data in a record that cannot change** (row 21, paragraph 104). That favours holding by reference over keeping ciphertext in the record. It was written for blockchains; that it carries to this store is inference.
- **The types can stop a copy, in part** (es-entity). This bears on Q5. Its opened reference still gives the plain value to the code that holds it.
- **After erasure, new data for that person is refused** by two systems. The plan did not have this.
- **Option E has no earlier example.** Systems mask or delete entries (rows 3, 10, 11). None runs the rest again.

## Not settled

- Whether a kept yes or no about a person (option C), or a kept fact (option B), is still that person's data. Nothing found speaks to it directly.
- Whether an authority accepts a destroyed key as answering a request to be erased (row 24). One accepts it for cleaning storage media; the French authority says it is not strictly erasure.
- Whether any language enforces "a write may not open, a reply may". None was found; that is a negative and proves nothing.
- Who uses ankka and es-entity, and whether either has met a real request to erase.
- Three things the recency member reported that Claude did not check: Marten 9.50.3 can delete a whole stream, Temporal has a proxy in preview that encrypts payloads at a gateway, and MongoDB's Queryable Encryption answers equality over random ciphertext.
- A quote the recency member gave for Cratis, "Erased values look like empty values", was not on the page Claude fetched. The page says the same thing in other words, quoted above.

# How have storage engines and databases been checked? (researched 2026-11-14)

This file adds to [research 08](08-correctness-first-databases.md) and the wiki pages on [deterministic simulation](../wiki/ideas/deterministic-simulation-testing.md), [formal design models](../wiki/ideas/formal-design-models.md) and [guarantees checked by a tool](../wiki/ideas/guarantees-checked-by-a-tool.md). It does not repeat FoundationDB, TigerBeetle's Jepsen report, SQLite's test harness or Amazon's 2015 DynamoDB result; those are on the wiki.

Facts about Mo come from `~/code/mo` (its `AGENTS.md`, `docs/agent-guide.md`, `models/`) and from [design-ideas.md](../design-ideas.md). Claims marked "inference" are my reasoning. "Vendor claim" marks what a company says about its own product.

## 1. Small executable models checked with generated tests

**Terms.** A *reference model* is a deliberately simple program that does what the real component should do, for example a plain map standing in for a tree on disk. *Property-based testing* generates many random inputs and checks a stated property on each. Its *stateful* form (also called *state-machine testing*) generates random sequences of operations, runs each on both the real code and the model, and compares them after every step. *Shrinking* cuts a failing sequence down to a short one that still fails.

**Amazon S3's ShardStore (SOSP 2021).** ShardStore is the storage node under S3: "over 40,000 lines of Rust", using soft updates for crash consistency, heavy concurrency and garbage collection (https://pm.inf.ethz.ch/publications/BornholtJoshiAstrauskas2021.pdf).

- *Method.* Reference models "written in the same language as the implementation and embedded in its code base". They are "1% of the implementation code"; "the reference model for a log structured merge tree implementation is a hash map". The models double as mocks in unit tests, "effectively requiring engineers to update the reference model specifications themselves" (same paper).
- *Durability split into three checks.* Sequential runs without crashes are checked for equivalence with the model; sequential runs with crashes use a model extended to say "which data can be lost after a crash"; concurrent runs without crashes are checked for *linearizability* (each operation appears to take effect at one instant between its call and its return) with separate models (same paper).
- *Crash checks.* Each write returns a `Dependency` that can be asked whether it is persistent. After a simulated crash ("DirtyReboot", with flushes of chosen components interleaved in the random sequence), every write whose dependency was persistent must still be readable with the right value. A variant that enumerated crash states block by block, as CrashMonkey does, "has not found additional bugs and is dramatically slower to test, so we do not use it by default" (same paper).
- *Concurrency.* The Loom model checker explores all interleavings of small, critical code; Shuttle, which Amazon wrote and open-sourced, samples interleavings randomly for tests too large for Loom (same paper).
- *Corrupt input from disk.* The Crux symbolic evaluator proved that deserializers "cannot panic" on any on-disk bytes up to a size bound, and fuzzing covered larger inputs (same paper).
- *Results.* "Our work has prevented 16 issues from reaching production, including subtle crash consistency and concurrency problems." "We routinely run tens of millions of random test sequences before every ShardStore deployment" (same paper). Several of the 16 were in chunk reclamation, the garbage collector: "Off-by-one error in reclamation", "Reclamation could forget chunks after a transient read IO error" (same paper, Figure 5).
- *Cost.* Reference models 450 lines; crash-consistency checks 2,661; concurrency checks 901; other unit and integration tests 19,540. The validation artifacts are "only 13% of the total code base and 20% of the size of the implementation code" (same paper, §8.2 and Figure 6). Amazon's own blog gives different figures, "about 14%" of the code base and "18% of the ShardStore specifications have been written by developers" (https://www.amazon.science/blog/aws-team-wins-best-paper-award-for-work-on-automated-reasoning); the paper says that after formal-methods experts wrote the first models, "they have been updated almost exclusively by the engineering team".
- *Misses.* Availability and performance were out of scope. One bug escaped to code review: tests never reached a cache-miss path "because the cache size was configured to be very large in all tests". Biasing generated arguments risks "baking our assumptions into our tests", so they bias only with "quantitative evidence" (same paper, §4.2, §8.3).

**The follow-up: S3 Express One Zone (SOSP 2026).** The same group applied the method to a distributed metadata index with distributed transactions (https://dl.acm.org/doi/pdf/10.1145/3830418.3843899; the ACM reference names the "ACM SIGOPS 32nd Symposium on Operating Systems Principles", Prague).

- New pieces: "a white-box approach to checking serializability" built from sequence numbers the implementation emits; checking data and control planes separately; and "long-running canaries that use reference models to check correctness across deployments" (same paper).
- *Cost.* Reference models "total just 4.8K lines, less than 2% of the 259K-line implementation"; harness and infrastructure 35.6K lines; all validation 40.4K lines, "16% of the implementation code" (same paper, §8.2).
- *What each layer added.* "In-memory sequential reftests caught 20 bugs that survived existing unit and integration tests, Shuttle-based concurrent reftests found 46 that survived the in-memory reftests, and persistent reftests found 10 that survived both prior layers" (same paper).
- *Who keeps it up.* After launch the engineering team's "share of validation commits has grown from 41% to 84%" over 2.5 years (same paper).
- *Misses, stated by the authors.* No latency or throughput; models "do not cover error cases such as resource exhaustion or device failures"; internal APIs only, so request parsing and authorization are out of scope (same paper, §8.4).

**Earlier stateful property testing.** QuickCheck's state-machine testing is the origin of the method.

- On *dets*, the disk store under Erlang's mnesia database: "We found five race conditions with relatively little effort, two of which may account for the observed failures in production" (https://research.chalmers.se/en/publication/150540; talk title "How I found five lurking race conditions in mnesia with 200 lines of QuickCheck code", https://www.erlang-factory.com/upload/presentations/427/HowIfound5raceconditions--JohnHughes.pdf).
- On Google's LevelDB, a compaction bug "required a long sequence of API calls to provoke it, but even so QuickCheck could find a minimal failing test in a few minutes" (vendor blog, https://www.quviq.com/blog/google-leveldb/).
- On AUTOSAR car software: "Testing code from 6 suppliers • 200+ issues identified • 100+ bugs identified in the standard" (slides, https://wiki.hh.se/ceres/images/8/83/Qcheck_in_industry.pdf). The bugs in the standard matter: writing the model exposes an unclear specification.
- Dropbox's sync engine: a generator builds random file trees and checks invariants, shrinking failures "QuickCheck"-style; "Every night we run tens of millions of randomized test runs" and a failing seed "is guaranteed to fail again" (https://dropbox.tech/infrastructure/-testing-our-new-sync-engine; https://www.infoq.com/news/2020/04/dropbox-testing-sync-engine/).

**The same method with a proof on the model side.** Cedar, Amazon's authorization language: an executable model in Lean, proofs about the model, and "differential random testing", "generating millions of random inputs and checking that both model and code produce the same output". "A new version of Cedar isn't released unless its model, proofs, and differential tests are up to date" (https://aws.amazon.com/blogs/opensource/lean-into-verified-software-development/, 2024-04-08). Mo's Lean model of Mo Core, compared with the VM on generated programs, is this pattern (`~/code/mo/AGENTS.md`).

**What this project would borrow.** The whole method, and Mo already has most of it: `mo test` generates call sequences, checks promises after every step and shrinks failures (`~/code/mo/docs/agent-guide.md`, lines 17 and 45). The missing pieces are a reference model per component, tiny sizes in tests (the cache lesson), coverage counts of rare paths, and a canary that keeps checking across upgrades (inference).

## 2. Deterministic simulation, beyond the wiki

The wiki covers what simulation demands and what FoundationDB and TigerBeetle found. Added here: how faults are shaped, what other users report, and one blind spot Mo's own crash check has.

**How the fake disk and network inject faults.**

- TigerBeetle's VOPR "uses a random seed to tune parameters for injecting different types of faults". It "may drop and reorder packets, partition the network, or corrupt reads and writes to the 'disk'" (https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/internals/vopr.md). Its safety page adds an explicit storage fault model: disks "experience data corruption with significant and material probability", and firmware may misdirect writes "to the wrong sector" (https://docs.tigerbeetle.com/concepts/safety/).
- **The shape of a fault decides what it finds.** The VOPR missed a bug about unchecked padding bytes because "when the VOPR injects a storage fault, it corrupts the whole sector -- if the padding is corrupt, then the header or body (or both) is also corrupt". "We missed this bug because we injected 'too many' faults!" The fix added "single-bit fault storage injection", which then "found another bug" (https://github.com/tigerbeetle/tigerbeetle/pull/2681). A separate change added misdirected-write faults to the VOPR (https://github.com/tigerbeetle/tigerbeetle/pull/2677).
- Amazon: deterministic simulation runs a distributed system "on a single-threaded simulator with control over all sources of randomness, such as thread scheduling, timing, and message delivery order". Tests can name orderings "that have caused bugs in the past", and the scheduler can fuzz or exhaust orderings (https://cacm.acm.org/practice/systems-correctness-practices-at-amazon-web-services/). The S3 Express team extended Shuttle with "failure injection, including cancelled operations and timeouts" (https://dl.acm.org/doi/pdf/10.1145/3830418.3843899).

**What users report.**

- Dropbox runs "millions of scenarios every day" against a deterministic control thread (https://dropbox.tech/infrastructure/rewriting-the-heart-of-our-sync-engine).
- Turso, a rewrite of SQLite, uses its own simulator and also runs Antithesis, "allowing us to catch a class of bugs that our simulator wouldn't catch (including bugs in the simulator itself)". It has since added a formal-methods product on top (vendor claim, https://turso.tech/blog/the-final-boss-of-reliability).
- Neither FoundationDB nor TigerBeetle publishes a count of bugs found (research 08). The S3 Express numbers above (46 bugs from Shuttle schedules) are the best published count I found for simulated concurrency (https://dl.acm.org/doi/pdf/10.1145/3830418.3843899).

**What it misses, added to the wiki's list.**

- A simulated disk only knows the lies it was told. One online book on simulation testing puts it plainly: "A simulated disk can faithfully replay a lie once a human has told it the lie exists; it cannot discover a lie it was never told about" (https://sunprema.github.io/books/books/deterministic-simulation-testing/concepts/09-limits-and-complementary-techniques.html, a secondary source). Section 3 shows where the real lies were found.
- A crash test that keeps the page cache is not a power cut. One engineer's write-up: `kill -9` "tests the program's own order of operations, with the page cache alive... It cannot find anything about durability, because the kernel keeps everything" (blog, https://www.mehdi.cz/blog/testing-crash-recovery-kill-9-fault-injection-and-simulation).
- Mo's recovery check "crashes and restarts the service on an in-memory store, and checks that each restart recovers the state the service held before its crash" (`~/code/mo/docs/agent-guide.md`, line 17). Inference: that is the `kill -9` kind of crash. A store that loses writes not yet synced, tears a write, or flips a bit would need a different check: that the restart recovers *some acknowledged* state, and never loses an acknowledged write.

**Borrow.** Seeded faults with explicit shapes (whole sector, single bit, torn, lost, misdirected) and a written fault model saying which combinations the system must survive (inference from the TigerBeetle sources).

## 3. Crash-consistency testing

**Terms.** *Crash consistency* means that after a power cut the stored data is in a state the program can recover from. *fsync* asks the operating system to push a file's data to the disk. A *torn write* is a write only partly on disk after a crash. *Persistence properties* are what a file system actually guarantees about the order and atomicity of writes after a crash.

**ALICE and BOB ("All File Systems Are Not Created Equal", OSDI 2014)** (https://www.usenix.org/system/files/conference/osdi14/osdi14-paper-pillai.pdf).

- BOB records block traces under a file system and reorders them to find which persistence properties hold. They "vary widely" across six Linux file systems: "appends to file A are persisted before a later rename of file B in the ordered journaling mode of ext3, but not in the same mode of ext4, unless a special option is enabled".
- ALICE records an application's system calls, generates every disk state the calls could leave after a crash, and checks the application's own invariants on each. Across "eleven widely-used systems (including databases, key-value stores, version control systems, distributed systems, and virtualization software)" it found "a total of 60 vulnerabilities", "roughly half" of which show up on ext3, ext4 and btrfs.
- What programs wrongly assume: when writes, "even to different files", are not persisted in order, "7 of the 11 tested applications have trouble properly recovering from a crash"; "10 of the 11 applications expect atomicity of file system updates". A single 512-byte write or a rename is atomic on many file systems; an append often is not (same paper).

**CrashMonkey and ACE (OSDI 2018)** (https://www.usenix.org/system/files/osdi18-mohan.pdf). A study of five years of reported file-system crash bugs found "most reported bugs can be reproduced using small workloads of three or fewer file-system operations on a newly-created file system, and that all reported bugs result from crashes after fsync() related system calls". So ACE generates every workload within such bounds and CrashMonkey simulates a crash after each persistence point. The tools found "24 out of the 26" reported bugs. The project lists "8 previously undiscovered bugs in btrfs, 2 in F2FS, and 1 bug in FSCQ", a verified file system (https://www.github.com/utsaslab/crashmonkey). Cost: "48 hours testing all 3.37 million workloads per file system on the 65-node research cluster" (paper).

**fsync failures.**

- "Can Applications Recover from fsync Failures?" (ATC 2020): some file systems "mark the relevant pages clean upon fsync failure, even though the dirty pages have not yet been written", so "retrying the failed fsync, will not work". Of PostgreSQL, LMDB, LevelDB, SQLite and Redis, "none are sufficient: fsync failures can cause catastrophic outcomes such as data loss and corruption" (https://www.usenix.org/system/files/atc20-rebello.pdf).
- PostgreSQL's response, after the 2018 "fsyncgate": "PostgreSQL will now PANIC on fsync() failure", backpatched to 9.4. On Linux, "you still only get the error once (so retrying fsync() is not OK)" (https://wiki.postgresql.org/wiki/Fsync_Errors).

**Corruption in replicated storage.** "A single file-system fault can induce catastrophic outcomes in most modern distributed storage systems", including "the spread of corruption to other intact replicas", across eight systems (FAST 2017, https://www.usenix.org/system/files/conference/fast17/fast17-ganesan.pdf). The follow-up, protocol-aware recovery, repairs a corrupt log entry from replicas using knowledge of the consensus protocol; unmodified LogCabin and ZooKeeper "can lose data or become unavailable" (FAST 2018, https://www.usenix.org/conference/fast18/presentation/alagappan). TigerBeetle cites both as the reason for its storage fault model (https://docs.tigerbeetle.com/concepts/safety/).

**Later tools.** LazyFS (VLDB 2024) is a file-system layer that simulates POSIX persistence and injects "lost and torn write faults" on demand. It was used on PostgreSQL, etcd, ZooKeeper, Redis, LevelDB, PebblesDB and Lightning Network to reproduce data-loss bugs; for example Redis's ACL file was "silently lost" after a lost write following a clean shutdown (https://www.vldb.org/pvldb/vol17/p3017-ramos.pdf). Ferrite (ASPLOS 2016) wrote formal "crash-consistency models" of file systems as litmus tests and used them to check and even place fsync calls (https://sandcat.cs.washington.edu/ferrite/; https://github.com/uwplse/ferrite).

**What a program may assume after a crash.** Putting the sources together:

- Not that writes reach the disk in the order issued, even across files (ALICE).
- Not that an append is atomic. A small aligned write and a rename usually are, on common file systems (ALICE).
- Not that fsync succeeded because a retry succeeded: after one failure, treat the file as lost and recover from the log (PostgreSQL wiki; ATC 2020).
- Not that the drive honoured the sync: "most consumer-grade mass storage devices lie about syncing". If a sync only orders writes, a crash can roll back committed transactions "but the database will at least continue to be consistent" (https://www.sqlite.org/howtocorrupt.html).
- Not that bits stay put: "disks will occasionally flip a bit in the middle of a sector" (same page), and firmware can misdirect writes (TigerBeetle safety page).

**Borrow.** Bounded, exhaustive small workloads (ACE's three operations); a crash after every fsync; fsync failure treated as fatal; checksums over every byte written. Inference: a tree of write-once nodes named by hash already detects most corruption, because a node whose bytes changed no longer matches its name. Bytes outside the hash, such as padding or the root pointer, are where TigerBeetle's lesson applies.

## 4. Checkers of histories and isolation

**Terms.** A *history* is the record of every operation clients sent and every answer they got. A checker asks whether some order of those operations explains every answer under a named model. *Serializability* means transactions appear to run one at a time in some order; *snapshot isolation* means each transaction reads one consistent past state and two transactions may not both change the same item.

**Why it is hard.** Knossos, Jepsen's original linearizability checker, must consider up to c! orders for c concurrent operations: "With 40+ concurrent processes, even histories of 5000 transactions were (generally) uncheckable in reasonable time frames". A constraint-solver approach to serializability became intractable past "a hundred-odd transactions" (Elle paper, https://www.vldb.org/pvldb/vol14/p268-alvaro.pdf). In general, checking serializability is NP-complete, and weaker levels such as read committed and causal consistency can be checked in polynomial time (summary matrix, https://naizhengtan.github.io/pages/isolation-checker-matrix.html).

**The tools.**

| Checker | What it shows | Reported results | Source |
| --- | --- | --- | --- |
| Hermitage | Hand-written two-session test cases that tell isolation levels apart, run against real databases | A table of what each database's named level actually prevents (PostgreSQL, MySQL, Oracle, SQL Server, FoundationDB and others) | https://github.com/ept/hermitage |
| Knossos | Linearizability of a single object's history | Exponential in concurrency (above) | Elle paper |
| Porcupine | Linearizability against a model written in Go | "Empirically, Porcupine is thousands of times faster than Knossos" | https://anishathalye.com/testing-distributed-systems-for-linearizability/; https://github.com/anishathalye/porcupine |
| Elle | Every anomaly in Adya's formalism except predicates, by choosing operations (such as appending to lists) whose reads reveal version order | Linear time; "revealed anomalies in every system we tested", four databases, "almost all" previously unknown | https://www.vldb.org/pvldb/vol14/p268-alvaro.pdf |
| Cobra | Serializability of a key-value store, with GPU pruning and an SMT solver | A reading group's summary: 10,000 transactions in about 15 seconds, about 2,000 per second sustained (secondary) | https://www.usenix.org/conference/osdi20/presentation/tan; https://charap.co/reading-group-cobra-making-transactional-key-value-stores-verifiably-serializable/ |

**What they can and cannot show.** A black-box checker sees only what clients saw, so it must guess the order and pays for the guessing; a checker that may read the system's own ordering (S3 Express) avoids the hard part. Every one of them finds only anomalies the workload provoked (research 08). Amazon also uses "post hoc validation of properties such as isolation (following approaches such as Elle)" (https://cacm.acm.org/practice/systems-correctness-practices-at-amazon-web-services/).

**Borrow.** The white-box form. Inference: the database planned here has one writer and a log in which every call names its root before and after, so the order is already written down. Checking a history means replaying each call alone and comparing roots, and re-running each recorded read against the root it named. That is linear and needs none of the solvers above.

## 5. Design models tied to the implementation

**Terms.** *Trace validation* (or trace checking) records the running code's steps and asks a model checker whether the model allows that sequence. *Model-based test generation* goes the other way: it enumerates the model's behaviours and turns each into a test of the code.

**Trace validation that worked: CCF (NSDI 2025).** Microsoft's Confidential Consortium Framework is "63 kLoC in C++". Its team wrote TLA+ models of consensus and of the log's consistency, then instrumented the code with "simple optional print statements" and used the TLC model checker to check that each test's trace matched the model (https://www.usenix.org/system/files/nsdi25-howard.pdf).

- *Found:* "six bugs in our consensus protocols, five concerning safety and one regarding liveness", fixed before production (https://decentralizedthoughts.github.io/2025-05-23-smart-casual-verification/).
- *Cost:* logging took "approximately one day"; a trace model that validated most traces "required approximately two engineer-months, spread over four months", much of it extending TLC (paper, §6.5).
- *What made it work:* the code and model had "different 'grains of atomicity'", so the trace model reuses the model's actions but enables each only when the next trace line matches. Searching depth-first made validating a trace take "less than a second using DFS, compared to about an hour with BFS" (paper).
- *Why it mattered:* "we were not confident that our consensus spec matched the implementation... we corrected safety violations present only in the spec, while the implementation contained bugs that spec verification could not find" (paper, §8).
- *Limits:* exhaustive model checking was too slow for continuous integration, so they added random simulation of the model; one bug stayed hidden in production only because operators happened to change membership one node at a time (paper).
- The general method, with case studies, is in Cirstea, Kuppe, Loillier and Merz, "Validating Traces of Distributed Programs Against TLA+ Specifications" (https://arxiv.org/abs/2404.16075).

**MongoDB: a failure, then two successes.**

- 2020, trace checking of the server: "This case study ended in failure: the project grew to cost more effort than it was worth". The causes named: "the system's enormous code size", "its complex internal concurrency control", and "the oversimplifications we had made when writing our TLA+" models (https://www.vldb.org/pvldb/vol13/p1346-davis.pdf; https://emptysqua.re/blog/extreme-modelling-in-practice/).
- 2020, test generation for a merge algorithm (the operational transformation of arrays in Realm Sync): for three elements and three clients the model produced 4,913 C++ tests, which "immediately achieved 100% branch coverage of the implementation, which we hadn't accomplished with our handwritten tests (21%) or millions of executions with the AFL fuzzer (92%)" (https://emptysqua.re/blog/extreme-modelling-in-practice/).
- 2025 and 2026, the storage engine: MongoDB modelled the interface between its distributed transactions and the WiredTiger storage engine as its own TLA+ module, then generated WiredTiger unit tests "by computing path coverings of the reachable state space". "For a small, complete finite model (2 keys and 2 transactions), we are able to check conformance with WiredTiger with a generated suite of 87,143 tests, which are generated and executed against the storage engine in around ~40 minutes" (https://www.mongodb.com/company/blog/engineering/towards-model-based-verification-key-value-storage-engine, 2026-02-27; paper https://www.vldb.org/pvldb/vol18/p5045-schultz.pdf; specs https://github.com/mongodb-labs/vldb25-dist-txns).
- Inference from the three: test generation works on a component with a small, clean interface; trace checking failed where the code's steps did not line up with the model's and succeeded (at CCF) when the team logged at the model's grain.

**Other model-based testing.** Mocket (EuroSys 2023) drives a Java implementation along paths from a TLA+ model's state graph; on ZooKeeper, Raft-java and Xraft it found "3 previously unknown bugs" (https://dl.acm.org/doi/10.1145/3552326.3587442). A review notes all three were in Xraft, a teaching implementation (http://muratbuffalo.blogspot.com/2023/08/model-checking-guided-testing-for.html).

**How industry uses TLA+ and its relatives, 2024 to 2026.**

- Amazon (CACM 2025): P, a language of communicating state machines, is used by teams on S3, EBS, DynamoDB, MemoryDB and Aurora. It was used to move S3 to strong read-after-write consistency, where it "helped eliminate several design-level bugs early". PObserve (2023) checks structured logs "both during testing and in production" against P models. Amazon.com "ran 733 FIS-based fault-injection experiments in preparation for Prime Day 2024". The barriers named are "steep learning curve and the specialized domain expertise required", and the authors expect language models to "help developers create formal models" (https://cacm.acm.org/practice/systems-correctness-practices-at-amazon-web-services/).
- Azure Cosmos DB: a TLA+ model of what users can observe was "significantly smaller and conceptually simpler than any other specification of Cosmos DB", and documented behaviours "previously poorly understood outside of the Cosmos DB development team" (ICSE SEIP 2023, https://fhackett.com/files/icse-seip-23-inconsistency.pdf; models https://github.com/tlaplus/azure-cosmos-tla).
- Published TLA+ models of databases also include TiKV's Percolator transaction protocol (https://github.com/pingcap/tla-plus/blob/master/Percolator/README.md), and the CockroachDB, Cosmos DB and MongoDB models already on the wiki.

**Borrow.** Test generation from the replay model, and trace validation of the call log. Inference: Mo's log already records one entry per call, which is the grain a replay model would use, so the obstacle that sank MongoDB's attempt is absent by design.

## 6. Full proofs of storage systems

**Terms.** A *proof assistant* (Coq, Lean, Isabelle) checks proofs written by people. An *auto-active verifier* (Dafny, Verus) asks for annotations and lets an SMT solver (an automatic prover for logic with arithmetic and data) do most of the steps. *Refinement* means every behaviour of the code is one the specification allows.

| System | What was proved | Proof against code | Cost and performance | Left out | Source |
| --- | --- | --- | --- | --- | --- |
| FSCQ (Coq, 2015) | A file system meets its specification under any crash, including crashes during recovery | "∼30,000 lines of verified code, specs, and proofs", against "∼3,000 lines" for the unverified xv6 file system | "Several researchers about a year and a half"; checking the proofs "takes 11 hours" | Concurrency; code is extracted to Haskell, so the Haskell compiler and runtime are trusted; CrashMonkey later reported a bug in FSCQ (location not confirmed) | https://pdos.csail.mit.edu/papers/fscq:sosp15.pdf; https://www.github.com/utsaslab/crashmonkey |
| Yggdrasil (Z3, 2016) | "Crash refinement" of the Yxv6 journaling file system, a copy tool and a log, "no manual annotations or proofs" | A small file system: "200 lines of Python" | Yxv6 verifies in "under a minute"; a toy file system "took one of the authors less than four hours" and the verifier "caught two bugs" | "Single-threaded code" only; loops must be bounded; the Python-to-C compiler is unverified | https://www.usenix.org/system/files/conference/osdi16/osdi16-sigurbjarnarson.pdf |
| VeriBetrKV (Dafny, 2020) | A key-value store on a write-optimised Bε-tree, crash safety treated as a distributed-systems problem | "Proof : code ratio is ~ 7" | Insertion "24× faster than unverified BerkeleyDB and 8× slower than RocksDB" | Trusts Dafny, its C++ compiler and an environment model | https://www.usenix.org/system/files/osdi20-hance.pdf; https://files.usenix.org/s3fs-public/cdn/osdi20_slides_hance.pdf |
| GoJournal (Perennial, Coq, 2021) | A concurrent, crash-safe journal in Go | Not confirmed | "We found one serious concurrency bug, even though GoJournal has many unit tests"; NFS server on it at "least 90%" of Linux NFS on ext4 | The NFS server on top (GoNFS) was unverified | https://www.usenix.org/system/files/osdi21-chajed.pdf |
| DaisyNFS (Perennial and Dafny, 2022) | A concurrent, crash-safe NFS file system: transactions proved in Perennial, each operation proved sequentially in Dafny | "Proof overhead of about 2× for the file system part (vs. 20× for the transaction system)"; transaction system 1,600 lines, file system 4,000 | "At least 60% the throughput of the Linux NFS server exporting ext4" | | https://www.usenix.org/system/files/osdi22-chajed.pdf |
| vMVCC (Perennial, 2023) | Linearizable multi-version transactions | Not confirmed (my copy of the text was cut) | "25–96% the throughput of Silo"; proving found "several bugs in corner cases" | Data lives in memory only | https://www.usenix.org/conference/osdi23/presentation/chang; https://www.usenix.org/system/files/osdi23-chang.pdf |
| CapybaraKV (Verus, 2025) | Functional correctness, crash consistency and corruption detection of a persistent-memory key-value store | Not confirmed | "Verify in under a minute"; "performance competitive with similar unverified PM KV stores" | "Arbitrary fine grained concurrency involving concurrent writes to the same storage region" | https://www.usenix.org/system/files/osdi25-leblanc.pdf; https://github.com/microsoft/verified-storage |

**What proofs miss.** A study of three verified distributed systems found "16 bugs, many of which produce serious consequences", almost all in the unverified "shim layer" and in assumptions about the environment, three of 11 shim bugs "related to resource limits" (EuroSys 2017, https://cs.purdue.edu/homes/pfonseca/papers/eurosys2017-dsbugs.pdf). The lesson matches section 3: the proof is only as good as the model of the disk and the network.

**Borrow.** DaisyNFS's split: hard reasoning (crashes and concurrency) once, in a small transaction layer; easy, sequential reasoning for everything on top (inference: Mo's one-writer design puts most code in the easy half already). Do not borrow a full proof of the engine now; ratios of 2× to 20× proof per line and years of expert time are not a one-person budget (inference from the table).

## Where the wiki is wrong or thin

- **[formal-design-models.md](../wiki/ideas/formal-design-models.md) is thin and leaves a wrong impression.** It reports MongoDB's failed trace checking and says only that test generation "did work for a smaller algorithm". It has none of the successes: CCF's trace validation found six bugs for about two engineer-months (https://www.usenix.org/system/files/nsdi25-howard.pdf); MongoDB's generated tests reached 100% branch coverage where hand-written tests reached 21% (https://emptysqua.re/blog/extreme-modelling-in-practice/); MongoDB's 2026 WiredTiger work generated 87,143 tests (https://www.mongodb.com/company/blog/engineering/towards-model-based-verification-key-value-storage-engine). A reader would conclude that tying models to code fails; the sources say it fails when the code's steps do not line up with the model's.
- **[guarantees-checked-by-a-tool.md](../wiki/ideas/guarantees-checked-by-a-tool.md) is thin.** It names only Elle and Hermitage. It lacks the cost of checking (exponential for Knossos, NP-complete in general for serializability), the later checkers (Porcupine, Cobra, PolySI, Viper, Plume), and white-box checking, which is the form that fits a system that owns its own log (section 4). It also groups Hermitage with checkers of histories; Hermitage is a fixed suite of hand-written tests (https://github.com/ept/hermitage).
- **[deterministic-simulation-testing.md](../wiki/ideas/deterministic-simulation-testing.md) is thin on fault injection.** It says the VOPR "injects network and disk faults" but not how, and misses the lesson that a fault's shape decides what it finds (https://github.com/tigerbeetle/tigerbeetle/pull/2681). It lacks Dropbox and the S3 Express Shuttle count. Its Mo entry lists missing disk faults but not that the recovery check's crash keeps every write, a `kill -9` crash rather than a power cut (inference from `~/code/mo/docs/agent-guide.md`, line 17).
- **The same page and [tigerbeetle.md](../wiki/systems/tigerbeetle.md) credit TigerBeetle with "a moving crash point".** The TigerBeetle sources I read describe faults injected with probabilities tuned by the seed, not a crash point moved forward one write at a time as in SQLite (https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/internals/vopr.md). I could not confirm the moving crash point for TigerBeetle.
- **No wiki page covers crash-consistency testing** (ALICE, CrashMonkey, fsync failures, LazyFS), **full proofs of storage systems**, or **reference models with generated tests**. Each deserves an idea page; the third is the instrument [design-ideas.md](../design-ideas.md) already ranks second.
- **A disagreement to record.** [design-ideas.md](../design-ideas.md) says Cedar's authors "formalized Cedar in Lean". Amazon's CACM 2025 article says "the implementation was built in the verification-aware programming language Dafny" (https://cacm.acm.org/practice/systems-correctness-practices-at-amazon-web-services/). Amazon's 2024 blog says "Over the past 6 months, we built a formal model of Cedar in Lean" (https://aws.amazon.com/blogs/opensource/lean-into-verified-software-development/). The likely reading is that Cedar moved from Dafny to Lean (inference); the CACM text describes the earlier state.
- **[jepsen.md](../wiki/systems/jepsen.md) and [antithesis.md](../wiki/systems/antithesis.md)** are accurate as far as they go. Small additions: Amazon validates isolation "following approaches such as Elle" (CACM 2025), and Turso runs Antithesis to catch bugs "in the simulator itself" (vendor claim, https://turso.tech/blog/the-final-boss-of-reliability).

## A checking plan for this project

The setting: one person with AI agents, building (a) a storage engine of write-once nodes named by hash plus a log of calls, and (b) a protocol that merges an agent's world by replaying its calls. Mo already has a Lean model of its core compared with the VM, three small TLA+ models with configurations meant to fail, `mo test` with generated inputs, promises checked after every step, shrinking and `--strength`, deterministic simulation of services, fuzz targets, CBMC proofs and sanitizers (`~/code/mo/AGENTS.md`). Everything below is my recommendation (inference), resting on the sources above.

**Add, in this order.**

1. **A reference model for each part, written in Mo, checked by `mo test` on generated call sequences.** For the engine the model is a plain map per version: a list of maps, one per root. For the merge protocol the model is "apply the landed calls to the main line in log order, checking promises after each". Compare after every step, as ShardStore does. Run with tiny node sizes so that splits, deep paths and garbage collection happen in short sequences (the cache lesson). This is ShardStore's cheapest layer, and it caught the most bugs per line at S3 Express. Agents can write both models; Robert reads them, because a model is the definition of right.
2. **The TLA+ model of the replay rule**, as [design-ideas.md](../design-ideas.md) already plans, with predictions first and configurations meant to fail. Keep it small: SysMoBench shows agents model small systems well and large ones badly. Then **generate Mo tests from it**: enumerate the small model's behaviours and turn each path into a call sequence for the Mo sketch, as MongoDB did for WiredTiger. Both sides are deterministic, so a mismatch replays exactly.
3. **A simulated disk with a written fault model**, under `mo test`, replacing the in-memory store's "keep everything" crash. On a crash it drops writes not yet synced, may tear the last write, and may flip one bit or misdirect one write. A failed sync is fatal, as in PostgreSQL. The check after restart: the state equals the model at some acknowledged point, and no acknowledged call is lost. Crash with a random subset flushed, as ShardStore does; do not enumerate block orders, which found nothing more there. Aim it first at garbage collection of old nodes and at the root switch: ShardStore's bugs clustered in reclamation, and TigerBeetle's in bytes no checksum covered. Count how often each rare case is reached, so a blind spot shows as a zero.
4. **A white-box history check over the log.** Every log entry names its root before and after, and every relied-on read records its answer. The checker replays each call alone and re-runs each read against the root it named. This is the S3 Express idea, at linear cost, and it doubles as a consistency check of stored data on start-up or on demand. Once reads run beside the writer, the same check covers them.
5. **A canary across upgrades.** A long-running Mo service holding Robert's real data, with the reference model running beside it, checked across every `mo push`. S3 Express's persistent canaries found 10 bugs that two earlier layers missed.
6. **One run on a real file system**, once Mo can write bytes and sync files. Run the engine under a fault-injecting file layer such as LazyFS, or cut power to a test machine, to test the simulated disk's beliefs. While SQLite is the byte store, the simulated store should model SQLite's contract (a committed transaction survives whole), not a raw disk.
7. **Lean statements for claims about the language**, as design-ideas already plans ("a helper's grant never shows more than the grant it was made from"). Prove them when the feature is in the reference. One experiment is worth trying later, and only later: let an agent prove one invariant of one pure tree function. Lowering to Mo Core text, which Lean already reads, might allow it (inference, `~/code/mo/AGENTS.md` names the Core text exchange). The ultima_db and VeruSAGE results say such proofs are now days of agent time, not months.

**This differs from design-ideas in one place.** Design-ideas plans a TLA+ model of the order of writes to disk (its step 3). I would skip it. The design writes new nodes, then switches the root, so the protocol is two steps; the bugs the sources found in this area lived in code (padding, reclamation, a missed fsync), which only a check on the real code can see. Step 3 above checks the real code under the same crashes. Keep a TLA+ model in reserve for the day garbage collection runs alongside readers.

**Do not bother with, for now.**

- A full proof of the engine (FSCQ, VeriBetrKV style): 2× to 20× proof per line of code.
- Black-box isolation checkers (Elle, Cobra, PolySI, Plume) and Jepsen-style cluster tests: there is one writer, the log already holds the order, and Mo has no networking yet.
- Exhaustive block-level crash enumeration (CrashMonkey style): ShardStore found it slower and no more productive.
- Antithesis: Mo already controls time, randomness and order.
- P or Quint as a second model language beside TLA+: the cost is learning and keeping one more language in step, and nothing in this design needs it.
- Liveness models before the safety ones pass: agents handle liveness worst (SysMoBench).

## What this means for the project

- The instrument design-ideas ranks second (a model in the implementation's own language, checked with generated tests) has the best published record per line for storage: 1% to 2% of the code in models, dozens of bugs, and maintenance taken over by ordinary engineers. Mo already ships most of the machinery as `mo test` and promises.
- Mo's crash check keeps every write. Until it can drop unsynced writes, tear and corrupt them, a passing crash test says nothing about durability.
- Owning the log turns the hardest checks into easy ones. A black-box isolation checker fights an NP-complete problem; a database that writes down its own order checks a history by replaying it.
- Tying a model to code fails when their steps do not line up. Mo's log of calls lines up with a replay model by construction, which is a reason to expect trace validation and test generation to be cheap here (inference).
- Agents now write most proof annotations for systems code whose specification exists (81% of 849 tasks) but model large systems poorly. That favours many small models and specifications Robert reads, with the checker deciding.

# Earlier work on requests as programs, grants as views, and proving what a program can see (researched 2026-11-14)

The design in [design-ideas.md](../design-ideas.md) makes three proposals. A: a request is a small read-only program in the host language, checked and run on a snapshot under a work limit, with no query language. B: what a caller may read is a view function, and a helper's grant is a further function on top, so a narrower grant needs no approval. C: because the request is a program in a language with a checked core, "no accepted program can read outside its grant" can be proved once for every program.

This file adds what the wiki does not have. Purpose-based access control, Hippocratic databases and approval of writes belong to [ticket 25](../issues/25-earlier-work-on-purpose-and-approval.md) and are left out. Vendor claims are marked "vendor claim"; my own reasoning is marked "inference".

## A. A request is a program, and the database is part of the language

### PS-algol and Napier88: orthogonal persistence

- **What it is.** *Orthogonal persistence* means any value of any type can outlive the program that made it, with no code to save or load it. PS-algol added this to an existing language, S-algol, in 1983 ([An Approach to Persistent Programming, Computer Journal 26(4)](https://doi.org/10.1093/comjnl/26.4.360)). Napier88 went further: "Napier88 was designed as an integrated persistent programming system", with editors and compilers living inside the persistent store ([Napier88 reference](https://archive.cs.st-andrews.ac.uk/papers/download/MCK+99.pdf)).
- **The problem it solved.** "the user need never write code to move or convert data for long or short term storage" ([Napier88 reference](https://archive.cs.st-andrews.ac.uk/papers/download/MCK+99.pdf)).
- **What it found.** The same team, looking back in 2009: "Orthogonally persistent systems will not replace object-relational systems in the foreseeable future." They name a "'closed data format' criticism" of past systems, and suggest a future system should keep its data in a relational store so that "read-only access to the data could be permitted at the relational level" ([Orthogonal Persistence Revisited, ICOODB 2009, LNCS](https://archive.cs.st-andrews.ac.uk/papers/download/DKM09a.pdf); [DOI](https://doi.org/10.1007/978-3-642-14681-7_1)). The Napier88 authors also say "some of the decisions as to what is built into the language and what is supported by the environment are somewhat arbitrary" ([Napier88 reference](https://archive.cs.st-andrews.ac.uk/papers/download/MCK+99.pdf)).
- **What it cost, and what became of it.** It stayed in research. PJama, orthogonal persistence for Java, was the attempt at an "industrial-strength" platform; after four years its authors wrote that "the experiments to test the utility of orthogonal persistence are still in their early stages" ([PJama review, 2000](http://citeseerx.ist.psu.edu/viewdoc/summary?doi=10.1.1.10.6660)). PJama "could not make some types persistent due to restrictions in the abstract machine" ([Dearle et al. 2009](https://archive.cs.st-andrews.ac.uk/papers/download/DKM09a.pdf)). A 2000 position paper says it reviews "why orthogonal persistence has not been taken up widely" ([Persistence and Java — A Balancing Act, LNCS 1944](https://www.research.ed.ac.uk/en/publications/persistence-and-java-a-balancing-act/)); I read only its abstract, so its list of reasons is not confirmed here.
- **What it means here.** A warning, and the clearest one in this section. Data reachable only through one language is the criticism the field's own authors accept. The design already answers it partly: outsiders reach a shared store through tools ([idea 7](../design-ideas.md)). Inference: the answer is incomplete until some form of the data can be read without Mo, for example an export or a read-only view in a common format.

### MUMPS: a language with a database built in that is still running hospitals

- **What it is.** A procedural language whose variables can be *globals*, a hierarchical store kept on disk. "By 1967, the Massachusetts General Hospital Utility Multi-Programming System, or MUMPS, debuted." It "used abbreviated commands and hierarchical database to minimize memory use" and "remains the basis of systems at many large hospitals and banking institutions" ([MGH Laboratory of Computer Science](https://www.mghlcs.org/50th-anniversary)).
- **Where it runs.** The US Department of Veterans Affairs told Congress in 2023 that "VistA itself is written in an old programming language, Mumps" ([VA testimony, 2023-03-07](https://docs.house.gov/meetings/VR/VR11/20230307/115390/HHRG-118-VR11-Wstate-McCuneD-20230307.pdf)). Epic "relies on Caché as a core technology for its EHR software", and Epic's founder sat on the MUMPS Development Committee ([Healthcare IT News, 2015](https://www.healthcareitnews.com/news/what-does-intersystems-cache-have-do-epics-ehr)). Epic moved to InterSystems IRIS with its August 2020 release; InterSystems says Epic customers process "roughly 1.8 billion database accesses per second" (vendor claim, [InterSystems, 2020](https://www.intersystems.com/news/intersystems-iris-data-platform-adopted-by-epic-for-its-new-generation-of-high-performance-scalability-and-architecture-flexibility/)).
- **What it cost.** People. The VA: "There are few Mumps programmers today, Mumps is not taught in computer science classes, and the pool of Mumps programmers shrinks every year as they retire" ([VA testimony](https://docs.house.gov/meetings/VR/VR11/20230307/115390/HHRG-118-VR11-Wstate-McCuneD-20230307.pdf)). The VA is replacing VistA with Oracle Health's system ([VA press release, 2024](https://news.va.gov/press-room/va-awards-second-option-period-to-oracle-federal-electronic-health-record-modernization/)). And questions: a secondary guide says Epic copies its hierarchical store, Chronicles, every night into Clarity, a relational database, because tree structures suit one patient but not questions across many patients ([casrai guide, secondary, not confirmed with Epic](https://casrai.org/guides/epic-systems)).
- **What it means here.** Both support and warning. A language with its own database can last nearly sixty years. But even its most successful user keeps a second, relational copy for questions nobody wrote a routine for. That is the design's idea 8, "unplanned questions", met in production by keeping two copies.

### The business languages with a database built in

- **What they are.** Languages of the 1980s and 1990s where reading a record is a statement of the language. Progress's ABL is still sold: "ABL has four statements you can use to define a set of one or more database records: `FIND`, `FOR`, `REPEAT`, and `OPEN`" ([Progress OpenEdge docs](https://docs.progress.com/bundle/openedge-develop-abl-applications-128/page/Data-access-without-looping-the-FIND-statement.html)). kdb+ ships the language q with its own columnar store; "Q is the SQL-like, general-purpose programming language built on top of kdb+" (vendor claim, [KX](https://kx.com/products/kdb/)).
- **What became of them.** Microsoft's FoxPro FAQ: "There will not be another major release of Visual FoxPro", announced March 2007 ([Microsoft FAQ](https://learn.microsoft.com/en-us/previous-versions/visualstudio/foxpro/mt490297(v=msdn.10))). dBase and Clipper were not checked. ABL and q survive in niches (inference from the vendors' current pages).
- **What it means here.** These languages lost to general languages talking to SQL servers, not to a flaw in putting data access in the language. Why they lost was not established in this run; from memory, not confirmed: vendors bundled the language and the store, and when the vendor moved on, users were stranded.

Covered by the wiki ([GemStone/S](../wiki/systems/gemstone.md), [code inside the database](../wiki/families/code-inside-the-database.md)). Nothing new was searched.

### Queries written in the host language: Kleisli, LINQ, Links, Ur/Web, Mnesia's QLC

- **Kleisli (1990s).** A data-integration system whose query language CPL "is a functional query language whose surface syntax is based on the comprehension syntax" ([Kleisli, JFP 2000](https://www.cambridge.org/core/journals/journal-of-functional-programming/article/kleisli-a-functional-query-system/BDB5049BBB1F2263B2431C5DAF951DC3)). A *comprehension* is a way of writing "every x from here where this holds" inside a language. It "has proven especially useful for bioinformatics applications" ([Kleisli project](https://www.comp.nus.edu.sg/~wongls/projects/kleisli/index.html)).
- **LINQ (C#, 2000s).** Queries written in C# and translated to SQL. LINQ is "integrated with the programming language, making it amenable to static type checking, optimization and ... refactoring tools" ([Dearle et al. 2009](https://archive.cs.st-andrews.ac.uk/papers/download/DKM09a.pdf)).
- **What the theory found.** A 2013 paper reports that "for several of our examples, Microsoft's LINQ framework either fails to produce an SQL query or produces an avalanche of SQL queries". A *query avalanche* is one host query turning into many database queries. Their fix, normalising the query before translation, proves when "a host query is guaranteed to generate a single SQL query" ([A Practical Theory of Language-Integrated Query, ICFP 2013](https://homepages.inf.ed.ac.uk/jcheney/publications/cheney13icfp.pdf)).
- **Links and Ur/Web.** Links is one language for browser, server and database: "Links translates into JavaScript to run on the browser and SQL to run on the database" ([Links paper](https://links-lang.org/papers/links-fmco06.pdf)). Ur/Web is discussed under C, with UrFlow.
- **Mnesia's QLC.** In Erlang, "A query is expressed using Query List Comprehensions (QLCs)" over Mnesia or ETS tables ([qlc docs](https://www.erlang.org/doc/apps/stdlib/qlc.html)).
- **What it means here.** Support, with a better way shown. These systems kept the host language and still recovered a declarative core: the comprehension is a part of the program the compiler can recognise and plan. This is the design's third answer under idea 8, "a declarative form inside Mo", and the 2013 paper shows it needs a normalisation step proved correct, or the planner silently falls back to many small reads.

### Systems where the only way in is a function

- **H-Store and VoltDB.** "We would support stored procedures only", with serial execution in main memory ([Pavlo interview, SIGMOD Record, 2015](https://sigmodrecord.org/publications/sigmodRecord/1503/pdfs/09_profiles_Pavlo.pdf)). VoltDB's docs: "Encapsulating all transaction logic in a single stored procedure prevents application stalls mid-transaction" (vendor claim, [VoltDB docs](https://docs.voltdb.com/v11docs/UsingVoltDB/DesignProc.php)). That is the design's write side: data changes only through approved functions.
- **Fauna.** A database with its own functional language, FQL. It shut down in 2025: "Driving broad based adoption of a new operational database that runs as a service globally is very capital intensive", and investors found it "not possible to raise the capital needed" ([Fauna, 2025-03-19](https://fauna.com/blog/the-future-of-fauna); [InfoQ](https://www.infoq.com/news/2025/03/fauna-shuts-down/)).
- **Firestore security rules.** Covered under B.
- **What it means here.** Function-only write paths work and were fast. Fauna died of money, not of its model. Inference: the design's risk of this kind is reach, which [map.md](../map.md) already sets aside as a measure.

### Running a caller's program safely inside a database

- **Wasm user functions.** ScyllaDB accepts user functions in WebAssembly, but "WebAssembly UDFs are still experimental due to insufficient testing" ([ScyllaDB docs](https://docs.scylladb.com/manual/stable/cql/wasm.html)). SingleStore runs each Wasm function "in its own in-process sandbox" with 16 MB of memory by default (vendor claim, [SingleStore docs](https://docs.singlestore.com/cloud/reference/code-engine-powered-by-wasm/)). In both, the function is installed by the database owner, not sent with each request (inference from the docs' `CREATE FUNCTION` form).
- **Fuel.** *Fuel* is a count of steps a program may take. Wasmtime: if a call must "always either complete or trap with an out-of-fuel error, deterministically, then fuel with a fixed bound should be used", but "fuel instrumentation is somewhat expensive" ([Wasmtime docs](https://docs.wasmtime.dev/examples-interrupting-wasm.html)). Mo's work limit is the same idea and is already deterministic ([design-ideas.md](../design-ideas.md)).
- **Termination checked before running.** The Linux eBPF verifier proves a kernel program ends before it is loaded. Its complexity limit is "set to 1 million", and for a bounded loop "the verifier will check every permutation of the loop" ([eBPF docs, verifier](https://docs.ebpf.io/linux/concepts/verifier/); [loops](https://docs.ebpf.io/linux/concepts/loops/)). The price is that programs are bent to fit the checker.
- **Metered programs against shared state: Ethereum.** Every operation costs *gas*. In 2016 attackers found operations priced below their real cost, and EIP-150 "aggressively raised certain gascosts ... to protect against DoS attacks" ([Ethereum blog, 2016](https://blog.ethereum.org/2016/10/13/announcement-imminent-hard-fork-eip150-gas-cost-changes); [EIP-150](https://eips.ethereum.org/EIPS/eip-150)). The reads from disk were what was underpriced: "it takes a long time to read from disk" ([Ethereum blog, 2016-09-22](https://blog.ethereum.org/2016/09/22/transaction-spam-attack-next-steps)).
- **A static cost check on a client's request.** GitHub's GraphQL API refuses before running any call that would "request more than 500,000 total nodes" ([GitHub docs](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api)).
- **What it means here.** Support, plus a precise warning. A step limit stops a runaway program. It does not stop a program that stays under the limit while doing the expensive thing many times. Ethereum shows the limit must count what is actually expensive, which for a store larger than memory is reads from disk, not interpreter steps (inference).

### Meteor, Dark and Unison

- **Meteor** bundles MongoDB collections with Minimongo, "an in-memory, all JS, implementation of the MongoDB API" on the client ([Meteor docs](https://docs.meteor.com/tutorials/data-loading/data-loading)). The store is MongoDB, an outside database.
- **Dark** made a language and hosted service where "It's extremely easy to have datastores and queues and HTTP handling" ([Dark devlog, 2020](https://blog.darklang.com/dark-devlog-1-fresh-start/)). Everything "was only available on that canvas, unshareable to anyone else" ([Darklang status update, 2024](https://blog.darklang.com/an-overdue-status-update/)). Dark Inc "ran out of money earlier this year" and was succeeded by Darklang Inc ([Darklang blog, 2025-06-16](https://blog.darklang.com/goodbye-dark-inc-welcome-darklang-inc/)).
- **Unison** stores data through the Unison Cloud platform: `Storage` "provides a common interface for running transactions in a database", with typed tables such as `OrderedTable` ([Unison Cloud core concepts](https://www.unison.cloud/docs/core-concepts/); [storage types](https://www.unison.cloud/docs/storage-solutions/)). Storage is reached through an *ability*, Unison's typed effect, which is close to a Mo capability (inference).
- **What it means here.** Dark is a direct warning: a language with built-in storage whose data and code could not leave its own hosted canvas.

## B. A grant is a view function, and a narrower grant needs no approval

### Views as access control: the Truman and non-Truman models

- **What it is.** A 2004 paper names two ways to use views as grants. In the *Truman model*, "the DBA defines a parameterized authorization view for each relation", and the user's query runs against that personal, restricted world. In the *non-Truman model*, the query runs unchanged only if it "can be answered using only the information contained in the authorization views"; otherwise it is rejected ([Rizvi et al., SIGMOD 2004](https://dl.acm.org/doi/pdf/10.1145/1007568.1007631)).
- **What it found.** The Truman model's flaw is "Inconsistencies between what the user expects to see and what the system returns" ([Purdue lecture on the paper](https://cs.purdue.edu/homes/ninghui/courses/Spring05/lectures/QueryModification.pdf)): a user who knows other students are in a course can get answers "inconsistent with such information" ([Rizvi et al.](https://dl.acm.org/doi/pdf/10.1145/1007568.1007631)). The non-Truman check is hard: deciding whether a query is answerable from views is undecidable "even for conjunctive views and queries" ([Blockaid, OSDI 2022](https://www.usenix.org/conference/osdi22/presentation/zhang)).
- **What it means here.** The design is the Truman model done by types: the agent's program runs on the view's result and cannot ask about anything else. That avoids the undecidable check entirely, which is a real gain. It keeps the Truman flaw: a count over the view looks like a count over everything. Inference: Mo can soften this, because the program's input type names the view, so the agent can be told it is counting "forms you may see", not "forms".

### Virtual private database and row policies: views applied by rewriting

- **Oracle VPD.** A policy function returns "a `WHERE` condition (called a predicate)" that the database adds to the user's statement ([Oracle docs](https://docs.oracle.com/en/database/oracle/oracle-database/26/dbseg/components-oracle-virtual-private-database-policy.html)).
- **Qapla (2017).** A reference monitor "intercepts all queries to the database ... and rewrites the queries to make them policy compliant"; policies "are specified in SQL, and stored in the database itself"; it "incurs moderate overheads" ([Qapla, USENIX Security 2017](https://www.usenix.org/system/files/conference/usenixsecurity17/sec17-mehta.pdf)). It relies "on the application to correctly tell Qapla which user" is asking.
- **PostgreSQL row policies** are on the wiki ([row and column security](../wiki/ideas/row-and-column-security.md)).
- **What it means here.** Rewriting is the Truman model in SQL. Its leaks come from what the optimiser does, next.

### How views leak: evaluation order, errors and timing

- **The 2006 finding.** When the optimiser runs a user's function before the access filter, the function sees hidden rows. "Error messages generated by some functions are another source of information leakage": a conversion that fails on a hidden value tells the user something about that value. Hiding exceptions "may change the behavior of queries, and more importantly, update transactions". The fix is a "safe" plan that runs such functions only on authorized rows ([Kabra, Ramamurthy, Sudarshan, SIGMOD 2006](https://dl.acm.org/doi/pdf/10.1145/1142473.1142489)).
- **PostgreSQL's own docs agree.** A function "that might throw an error depending on the values received ... could provide significant information about the unseen rows if applied before the security view's row filters". Even a `security_barrier` view is "secure only in the limited sense that the contents of the invisible tuples will not be passed to possibly-insecure functions". A user may "measure the run time of queries against the view", or see the plan with `EXPLAIN`; run time and plan choice reveal "the amount of unseen data, or even ... the data distribution". The protection costs speed: such views "may perform far worse", and an index cannot be used unless its operator is marked `LEAKPROOF` ([PostgreSQL docs, rules and privileges](https://www.postgresql.org/docs/current/rules-privileges.html)).
- **What it means here.** The design's "the cost is computing the view for each request" is exactly the price PostgreSQL pays to stay safe. The warning is about the moment it is optimised. Running the agent's filter inside the view, or computing the view lazily as the program asks for items, puts the agent's code next to hidden rows, and errors, timing and the work count can then depend on them (inference). Every optimisation of a view must keep the agent's code on the output side of the boundary.

### How views leak: answers that combine

- **Trackers.** A *statistical database* answers totals only and refuses small groups. The 1979 tracker paper showed "the compromise of small query sets can in fact almost always be accomplished with the help of characteristic formulas called trackers", and "Almost all databases have a general tracker, and general trackers are almost always easy to find" ([Denning, Denning, Schwartz, ACM TODS](https://faculty.nps.edu/dedennin/publications/TrackerThreat.pdf); [DOI](https://dl.acm.org/doi/10.1145/320064.320069)). A *tracker* is a pair of allowed large questions whose difference is the forbidden small one.
- **Reconstruction.** "in order to achieve privacy one has to add perturbation of magnitude Ω(√n)" ([Dinur and Nissim, PODS 2003](https://dl.acm.org/doi/10.1145/773153.773173)). In plain terms: if enough totals are answered too exactly, the rows themselves can be rebuilt.
- **What it means here.** A direct hit on idea 9's example release function, "average over at least ten". A minimum group size is the defence the tracker paper broke. The wiki already sends this to [differential privacy](../wiki/ideas/differential-privacy.md). New here (inference): the design's ability to re-run a past question against an old snapshot is itself a differencing tool. The same count before and after one change reveals the change.

### Object-capability narrowing: wrappers, caretakers, membranes

- **What it is.** A *capability* is an unforgeable reference that is also the permission. Narrowing is done by putting a program in between: "programmers control access partially by manipulating the access graph, and partially by writing programs whose behavior attenuates the authority that flows through them" ([Miller, Robust Composition, 2006](https://papers.agoric.com/assets/pdf/papers/robust-composition.pdf)). "Redell's caretaker" (1974) is a forwarder that can be switched off, which gives revocation. A *membrane* "additionally wraps each capability (non-data reference) passing in either direction in a caretaker, where all these caretakers revoke together" ([Miller 2006](https://papers.agoric.com/assets/pdf/papers/robust-composition.pdf)).
- **In a shipping database.** Convex's row security is a wrapper of this kind: `wrapDatabaseReader` and `wrapDatabaseWriter` "create wrapped database instances with RLS enforcement", checked "whenever code tries to read or write the row" ([Convex Stack](https://stack.convex.dev/row-level-security); [convex-helpers](https://github.com/convex/convex-helpers)).
- **What it found.** Miller's point is that a wrapper's limit is "partially behavioral": you have to read the wrapper to know what it lets through ([Miller 2006](https://papers.agoric.com/assets/pdf/papers/robust-composition.pdf)).
- **What it means here.** Support, and a sharper claim than the capability literature makes. A forwarder can pass a reference through, so its narrowness depends on its code. A view function returns plain data, and Mo values hold no capabilities in a service's state ([design-ideas.md](../design-ideas.md)). So anything a helper computes from `g(f(data))` could have been computed from `f(data)`. That is why "narrower is free" holds by structure, with no analysis of `g` (inference). The membrane's lesson still applies to revocation: one switch must end every grant made from a grant, which the design already says.

### Credentials the holder narrows: Macaroons, Biscuit, UCAN

- **Macaroons (2014).** "Macaroons: Cookies with Contextual Caveats for Decentralized Authorization in the Cloud", by Arnar Birgisson, Joe Gibbs Politz, Úlfar Erlingsson, Ankur Taly, Michael Vrable and Mark Lentczner, NDSS 2014 ([NDSS](https://www.ndss-symposium.org/ndss2014/ndss-2014-programme/macaroons-cookies-contextual-caveats-decentralized-authorization-cloud/); [DOI](https://doi.org/10.14722/ndss.2014.23212)). "their bearer can delegate parts of their authority to other principals by deriving new macaroons that both attenuate the accessible aspects of the target service and also restrict ... from where, by who, and with what extra evidence" ([paper](https://www.ndss-symposium.org/wp-content/uploads/2017/09/04_3_1.pdf)). The chain is built with HMACs, so "Macaroon validation requires knowing the secret key used to generate the initial token" ([Clever Cloud on Biscuit, 2021](https://www.clever.cloud/blog/engineering/2021/04/12/introduction-to-biscuit/)).
- **Biscuit** takes the same design "with public key cryptography", so any service with the public key can check it ([Clever Cloud](https://www.clever.cloud/blog/engineering/2021/04/12/introduction-to-biscuit/)). "Offline attenuation unlocks powerful delegation patterns, without needing to support them directly in the origin service" ([Biscuit docs](https://doc.biscuitsec.org/getting-started/introduction.html)).
- **UCAN.** A chain of signed delegations in which "Each direct delegation MUST either directly restate or attenuate (diminish) its capabilities" ([UCAN spec](https://github.com/ucan-wg/spec)). Two cautions from its own documents. An older guide allows an exception: "except for rights amplification" ([Fission guide](https://fission.codes/blog/a-guide-to-ucans/)). And on revocation: "If an Agent is able to construct a valid proof chain without relying on the revoked proof, they still have access" ([UCAN revocation](https://ucan.xyz/revocation/)).
- **What it means here.** Support. All three let a holder narrow without asking the issuer, which is "narrower is free". They narrow by adding conditions that the service checks; the design narrows by adding a function the service runs. The design's version says what data is visible, not only which calls are allowed (inference). UCAN's revocation caution applies directly: if a helper can hold two grants that reach the same data, taking one back does not end its access.

### Zanzibar: relationships checked centrally, for contrast

- **What it is.** Google's authorization service. Each check asks a central service whether a relation holds. It "has maintained 95th-percentile latency of less than 10 milliseconds and availability of greater than 99.999% over 3 years of production use" (vendor claim, [Zanzibar, USENIX ATC 2019](https://www.usenix.org/system/files/atc19-pang.pdf)).
- **What it found.** The "new enemy" problem, which "can arise when we fail to respect the ordering between ACL updates or when we apply old ACLs to new content". Zanzibar prevents it with snapshot reads whose staleness is bounded by a token, the *zookie* ([Zanzibar paper](https://www.usenix.org/system/files/atc19-pang.pdf)).
- **What it means here.** A better way shown on one point. The design runs a read on a snapshot. Inference: the grant must be read at the same moment as the data, so that a grant withdrawn before the snapshot is never used on it, and a long-running read against an old snapshot must state which version of the grant it ran under. The design's TLA+ claim covers writes under withdrawn grants; it should cover reads too.

### View functions as read permissions, shipping in 2025: SpacetimeDB

- **What it is.** SpacetimeDB 1.8.0 (2025-11-12) added "Module Defined Views": "Views are a simple, but incredibly expressive way to define custom and intricate read permissioning for your tables." They "are defined by read-only procedural, functions in the language of your module". In the first release "Mutations are not allowed" and "Full table scans are not allowed", so that the database can "efficiently compute the real-time delta". The same release says "we will be deprecating the RLS API in favor of the view API" ([release v1.8.0](https://github.com/clockworklabs/SpacetimeDB/releases/tag/v1.8.0)). "Private tables can only be accessed by reducers and views running on the server" ([access permissions](https://spacetimedb.com/docs/tables/access-permissions/)).
- **What it means here.** The strongest support found for B. A shipping database replaced row-level rules with read-only view functions in the host language. Its restriction, no full scans, is the cost the design names ("computing the view for each request"), paid in a different coin: it limits what a view may be so the view can be kept current. That matches the design's open question, "which form of view the database can keep current". SpacetimeDB's clients still query views with SQL subscriptions; they do not send programs (inference from the docs).

### Firestore: rules that are not filters

- "If a query could potentially return documents that the client does not have permission to read, the entire request fails." Firestore "evaluates the query against its potential result set and not the actual field values" ([Firebase docs](https://firebase.google.com/docs/firestore/security/rules-query)). This is the non-Truman model in a large shipping service. It costs developers: a query that is correct for the data present still fails if it could reach other data.

## C. Proving that a program sees only what its view allows

### UrFlow and Ur/Web (2010): policies as queries, checked before running

- **What it is.** A checker for Ur/Web programs. "an application's confidentiality policy is a fixed set of queries, whose results provide an upper bound on what information may be released to the user". It uses "symbolic evaluation and automated theorem-proving", needs "no program annotations (beyond the policies themselves)" and adds "no run-time overhead" ([UrFlow, OSDI 2010](https://adam.chlipala.net/papers/UrFlowOSDI10/)).
- **What it found.** It claims "fully sound static assurance about all possible executions of a program" ([UrFlow](https://adam.chlipala.net/papers/UrFlowOSDI10/)). It worked because Ur/Web gives database access "first-class status"; the author names adapting it to other languages as future work ([UrFlow](https://www.usenix.org/conference/osdi10/static-checking-dynamically-varying-security-policies-database-backed-applications)).
- **What it means here.** The closest earlier statement of B: a grant is a set of queries that bounds what may leave. UrFlow proves it per program, with a theorem prover. The design would get it by typing: the program never receives anything else. Support.

### SeLINQ (2014): a proof across the language and the database

- **What it is.** A security type system for F# programs with LINQ queries, proved to enforce *noninterference*, which "formalizes computational independence between secrets and non-secrets" ([SeLINQ, ICFP 2014](https://schoepe.org/~daniel/icfp14.pdf)).
- **What it leaves out.** "noninterference is termination-insensitive in the sense that leaks via the observation of (non)termination are ignored" ([SeLINQ](https://schoepe.org/~daniel/icfp14.pdf)). How much that leaves out: "in the presence of output, the price is higher than the 'one bit' often claimed informally in the literature, and effectively such programs can leak all of their secrets" ([Askarov et al., ESORICS 2008](https://askarov.net/esorics08.pdf)), though not reliably in polynomial time for large secrets.
- **What it means here.** A warning about how the theorem is stated. A request that hits the work limit and stops is a termination the caller sees. Inference: the theorem should say that two databases whose views are equal give the same reply, the same error and the same work count. Mo is deterministic and the program sees only the view's output, so this stronger form may cost little to prove for the program; the view function itself is where it can fail.

### Jacqueline (2016) and Hails (2012): enforcement at run time

- **Jacqueline** attaches policies to fields and uses *faceted execution*, which "propagates labels through all derived values, conditionals, and variable assignments to prevent indirect and implicit flows", into the database ([Jacqueline, PLDI 2016](https://dl.acm.org/doi/10.1145/2980983.2908098); [talk](https://www.cs.cmu.edu/~jyang2/talks/pldi2016_jacqueline.pdf)). "For one case, the Jacqueline implementation performs better than an implementation with hand-coded policies" ([talk](https://www.cs.cmu.edu/~jyang2/talks/pldi2016_jacqueline.pdf)).
- **Hails** runs untrusted web applications over a shared, labelled database, using "thread-level dynamic information flow control". It ran a public site, GitStar, with third-party authors. Only "about 4,000 modules in Hackage (27%)" were safe for its applications to import ([Hails, OSDI 2012](https://www.usenix.org/system/files/conference/osdi12/osdi12-final-35.pdf)).
- **What it means here.** Hails is the nearest earlier system to "many outside programs, one shared store, a policy that travels with the data". Its 27% figure is the cost of a language subset that is safe to run. Mo has no unsafe escape and no ambient authority, so that cost may already be paid (inference).

### Storm (2021): policies as refinement types

- **What it is.** Storm writes the policy into the data model and generates a typed data layer; LiquidHaskell, a *refinement type* checker (types with logical conditions attached), then checks "statically and automatically" that the application obeys it ([Storm, OSDI 2021](https://www.usenix.org/system/files/osdi21-lehmann.pdf)).
- **What it means here.** Support for checking at compile time, with an off-the-shelf solver doing the logic.

### Blockaid (2022): checking each query against views before it runs

- **What it is.** "A Blockaid policy consists of SQL view definitions that specify what information can be accessed by a given user". The application queries base tables as usual, and "If a query's output might depend on information outside the views, Blockaid must block the query". It "verifies policy compliance using SMT solvers and generalizes and caches previous compliance decisions" ([Blockaid, OSDI 2022](https://www.usenix.org/conference/osdi22/presentation/zhang); [code](https://github.com/blockaid-project/blockaid)).
- **What it cost.** The exact check is undecidable, so Blockaid works per request trace with a solver and a cache. Applications "must be modified to fetch only data known to be accessible" to avoid "spurious errors" ([Blockaid](https://www.usenix.org/conference/osdi22/presentation/zhang)).
- **What it means here.** Blockaid is the non-Truman model built well, and it shows the price: a solver on the request path and programs rewritten to please it. The design avoids both by giving the program only the view. That is the design's real advantage over this line of work (inference).

### Multiverse databases (2019) and Sesame (2024): the view computed by the database

- **Multiverse databases.** Each user gets a "parallel universe" computed by dataflow, so "Application code executing for a user can safely execute any query against the user's parallel universe database without risk of seeing ... forbidden data". The system pushes "the universe boundary as far 'down' the queries' dataflow as possible while still maintaining correctness"; the prototype "supports thousands of parallel universes on a single server" ([Towards Multiverse Databases, HotOS 2019](https://dl.acm.org/doi/10.1145/3317550.3321425); [summary](https://blog.acolyer.org/2019/06/17/towards-multiverse-databases/)).
- **Sesame.** "A policy container is a wrapper type that protects the wrapped data", and code that uses it must run in *privacy regions* checked by static analysis or a sandbox. "Sesame's automated guarantees cover 95% of application code, with the remaining 5% needing manual review", at "3–10% performance overhead (10–55% with sandboxes)" ([Sesame, SOSP 2024](https://cs.brown.edu/people/malte/pub/papers/2024-sosp-sesame.pdf)).
- **What it means here.** Multiverse is the design's "an index is a view the database keeps current" applied to grants, and its "push the boundary down" is the same optimisation risk named under B. Sesame is close to idea 9's release functions: wrapped data, released only through reviewed code, with human review aimed at the few places that need it.

### PINQ (2009): caller-written programs with a proof, and how the proof was broken

- **What it is.** Privacy Integrated Queries. "Analysts then write arbitrary C# programs, writing queries over PINQ data sources almost as if they were using unprotected LINQ data sources", and the platform gives "formal guarantees of differential privacy for any and all uses of the platform" ([PINQ, Microsoft Research](https://www.microsoft.com/en-us/research/project/privacy-integrated-queries-pinq/); [SIGMOD 2009](https://dl.acm.org/doi/10.1145/1559845.1559850)).
- **What was found.** Two years later, systems like it were shown "vulnerable to a variety of covert-channel attacks that can be exploited by an adversarial querier", through timing, the privacy budget and global state ([Differential Privacy Under Fire, USENIX Security 2011](https://www.usenix.org/conference/usenix-security-11/differential-privacy-under-fire)). The defence, Fuzz, forces "a fixed timing on the query" ([CCS 2021 paper describing it](https://dl.acm.org/doi/pdf/10.1145/3460120.3484751)).
- **What it means here.** The strongest single warning in this run. PINQ is the earlier version of the design's own sentence: callers send programs in the host language, and a guarantee holds "for any and all uses". It was proved, and it was broken, because the proof's model did not include time, the budget or shared state.

### 2024 to 2026: scoped database access for AI agents

- **BridgeScope (2025)** splits database work into fine-grained tools aligned "with both database privileges and user security policies", and reports it "reduces token usage by up to 80%" (authors' claim, [arXiv 2508.04031](https://arxiv.org/html/2508.04031)).
- **Progent (2025)** checks each agent tool call against policies written in a small language: "Before each tool call is executed, Progent makes a decision to either allow or block it" ([arXiv 2504.11703](https://arxiv.org/html/2504.11703v2)).
- **SpacetimeDB views (2025)**, above, are the only shipping read-permission mechanism found that is a function in the application's language. It is not aimed at agents.
- **What it means here.** Agent work in 2024 to 2026 limits which calls an agent may make. None found gives an agent a typed view and proves its program stays inside it. The wiki's [CaMeL](../wiki/systems/camel.md) and FIDES work in the agent, not the database.

## Is "the request is a program" new, and why did earlier attempts lose?

It is an old idea under several names, put together in a new combination. "Database programming languages" (PS-algol, Napier88, MUMPS, ABL, q) made the store part of the language. "Language-integrated query" (Kleisli, LINQ, Links, QLC) wrote questions in the host language. "Code shipping" (PINQ, Convex queries, Wasm functions) ran a caller's code next to the data. PINQ already let callers send arbitrary host-language programs with a guarantee proved for all of them.

What is new is the combination: a request program from an untrusted agent, typed against a view, read-only, run on a snapshot under a deterministic work limit, and logged so it can be run again. I found no system with all of these (inference, from the systems above).

Earlier attempts lost for four reasons, in this order of weight:

1. **The data was closed.** Their own authors name the "closed data format" criticism of orthogonal persistence; Dark's data was "unshareable"; Epic keeps a relational copy beside its MUMPS store.
2. **Questions nobody planned.** Hand-written navigation is slow and brittle; LINQ needed a normalisation theory to avoid many small queries.
3. **Money and people.** Fauna and Dark ran out of capital; the VA cannot find MUMPS programmers; FoxPro was ended by its vendor.
4. **Safety of foreign code.** Wasm user functions are still "experimental"; Ethereum's limits were attacked where they priced work wrongly; PINQ's proof was broken by what it did not model.

None of them lost because a program is a worse request than a query.

## Is "a grant is a view function" sound, and how does it leak?

Sound in its core, with a condition. If the agent's program receives only `f(data)`, and Mo gives it no other way to reach anything, then whatever it returns is computed from `f(data)`. A helper's grant `g(f(data))` can then only show less, with no analysis of `g`. That is a structural property, and it is why the design avoids Blockaid's undecidable check (inference). UrFlow and SpacetimeDB are the nearest earlier forms.

The condition is that the boundary is real: nothing about the agent's run may depend on data that `f` left out. The three best-known ways such schemes leak:

1. **Errors, timing and evaluation order inside the view.** When the agent's code, or a filter it supplied, runs before or inside the view, a failure or a slow step on a hidden row tells it about that row ([Kabra et al. 2006](https://dl.acm.org/doi/pdf/10.1145/1142473.1142489); [PostgreSQL docs](https://www.postgresql.org/docs/current/rules-privileges.html)). The view function itself also runs on the full data, so its own errors, running time and work count are visible to the caller unless they are made independent of hidden data (inference).
2. **Allowed answers that combine.** Totals that each pass a minimum group size combine into a fact about one person ([trackers](https://faculty.nps.edu/dedennin/publications/TrackerThreat.pdf); [Dinur and Nissim](https://dl.acm.org/doi/10.1145/773153.773173)). Re-running a question against old snapshots is a ready-made way to take differences (inference).
3. **Termination and limits.** A program that stops at the work limit, or is refused, tells the caller something. Proofs of this kind usually leave it out ([SeLINQ](https://schoepe.org/~daniel/icfp14.pdf)), and it can leak far more than one bit ([Askarov et al.](https://askarov.net/esorics08.pdf)). PINQ's guarantee fell to timing, budget and state channels ([Differential Privacy Under Fire](https://www.usenix.org/conference/usenix-security-11/differential-privacy-under-fire)).

A fourth, already on the wiki, belongs to writes: a uniqueness check against hidden rows reveals that they exist ([row and column security](../wiki/ideas/row-and-column-security.md)).

- **[SpacetimeDB](../wiki/systems/spacetimedb.md) is out of date.** It has no word on view functions (1.8.0, 2025-11-12), which are now its read-permission mechanism, nor that its row-level security is experimental and being deprecated in their favour ([release](https://github.com/clockworklabs/SpacetimeDB/releases/tag/v1.8.0)).
- **[Access scoped to what an agent may do](../wiki/ideas/scoped-access-for-agents.md)** says "None as a database feature". SpacetimeDB's views are now a database feature for per-caller reads, though not built for agents. BridgeScope and Progent (2025) are missing.
- **[Row and column security](../wiki/ideas/row-and-column-security.md)** is thin. It covers only PostgreSQL. Missing: the Truman and non-Truman models; `security_barrier` and `LEAKPROOF` views and their cost; leaks through errors and timing (Kabra et al. 2006); Oracle VPD; Firestore's "rules are not filters"; Qapla and Blockaid. Its line that IFDB has labels "without covert channels" overstates the source, which says IFDB handles transactions and constraints "without introducing covert channels" ([IFDB](https://pmg.csail.mit.edu/pubs/schultz13__ifdb_decentralized_ifc-abstract.html)), not that it has none.
- **[Labels that follow data](../wiki/ideas/information-flow-labels.md)** lists only IFDB on the research side. Missing: UrFlow, SeLINQ, Jacqueline, Hails, Storm, Sesame, and the termination-insensitive caveat that most such proofs carry.

Missing: Macaroons and the secret-key verification that separates them; UCAN and its revocation caution; caretakers and membranes. Its line that "which agent may read which row is the database's own policy, built as data" is now in tension with the design's grants as Mo functions; it is not wrong as a description of today's Mo.
- **[Convex](../wiki/systems/convex.md)** does not say that access control is done by wrapping the database reader in user code ([Convex Stack](https://stack.convex.dev/row-level-security)).
- **[Erlang ETS and Mnesia](../wiki/systems/mnesia.md)** does not mention QLC, queries written as Erlang list comprehensions ([qlc](https://www.erlang.org/doc/apps/stdlib/qlc.html)).
- **[Set-at-a-time queries](../wiki/ideas/set-at-a-time-queries.md)** lacks language-integrated query and the 2013 normalisation result, which is the earlier work for idea 8's "declarative form inside Mo".
- **[Code inside the database](../wiki/families/code-inside-the-database.md)** lacks MUMPS, ABL and kdb+, orthogonal persistence (PS-algol, Napier88, PJama) and its "closed data format" lesson, H-Store and VoltDB's procedures-only design, and the ends of Fauna and Dark.
- **[Stored procedures and triggers](../wiki/ideas/stored-procedures-and-triggers.md)** presents them as a trap and lacks the counter-case: H-Store and VoltDB made them the only way in, on purpose, for speed.

## What this means for the project

1. **Keep B; it is the strongest of the three.** SpacetimeDB reached the same design in 2025 from a different direction, and UrFlow stated it in 2010. Running the program on the view's output is what spares the design Blockaid's solver and Firestore's rejected queries.
2. **Write one rule into the design now:** no optimisation may run the agent's code, or a filter it supplies, on the input side of a view. PostgreSQL, Kabra et al. and Multiverse all meet this at the moment they try to make views fast. It decides the form a view must take for the database to keep it current.
3. **State the Lean theorem in its stronger form.** Two databases with the same view give the same reply, the same error and the same work count. The usual termination-insensitive form is the gap PINQ fell through. Separately, make the view function's own failures and cost independent of data it hides, or count them as part of what the grant reveals.
4. **Release functions need more than a minimum group size.** "Average over at least ten" is the defence trackers broke. Use noise, as the wiki's differential privacy page says, or accept and record the risk. Re-running past questions on old snapshots needs the same care.
5. **Price the work limit by what is expensive.** Once data is larger than memory, reads from storage, not steps, are the cost; Ethereum's 2016 repricing is the lesson.
6. **Give the data a way out.** The persistence researchers' own verdict and Epic's nightly relational copy say the same: a store reachable only through one language is the thing that loses. Tools over MCP are a door for programs; an export in a common format is a door for everyone else.
7. **Tell the agent its answers come from a view.** The Truman model's flaw is silent: a count over what you may see looks like a count over everything.
8. **Read grants at the snapshot.** A withdrawn grant must never be applied to a snapshot taken after the withdrawal, and an old snapshot's read must name the grant version it ran under (Zanzibar's new enemy problem).
